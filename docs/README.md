# 文档索引

这个目录按**文档会不会腐化、以及腐化了要靠什么发现**分层。三类的维护策略互不相同——
把它们平铺在一起会导致一件坏事：要么用最严的规矩管住不需要管的，要么用最松的漏掉必须盯的。

| 目录 | 装什么 | 腐化风险 | 靠什么守 |
|---|---|---|---|
| [`reference/`](reference/) | 精确描述**当前实现**，给改代码的人和 agent 查 | **高**——代码一改就过时 | `tools/doc_audit.py` 机器对账 |
| [`methodology/`](methodology/) | 「怎么做这类工具」，换一个 harness 观测工具照样成立 | **低**——几乎不随本项目代码变 | 认知更新时才改，不进对账 |
| 本目录根下 | 元文档：讲文档体系自己 | 低 | 体系变了才改 |

## reference/ — 参考手册（进对账）

| 文档 | 什么时候看 |
|---|---|
| [架构总览.md](reference/架构总览.md) | 想搞懂这软件怎么搭起来的——模块怎么分层、数据怎么流过它们 |
| [开发指南.md](reference/开发指南.md) | **改代码前必读**：安全不变量、惯犯 bug、防御性设计、自测与静态对账清单 |
| [API契约.md](reference/API契约.md) | 接口规格——端点 / 字段 / 枚举的真源 |
| [界面导览.md](reference/界面导览.md) | 4 个视图各看到什么、数据从哪来 |
| [AI_USAGE.md](reference/AI_USAGE.md) | 用 agent 驱动本工具（这份随产物打包，`--help` 与 `GET /api/ai-guide` 交出的就是它） |

**为什么这一类要机器对账**：它们承诺「代码现在就是这样」。这个承诺没有任何东西自动维持——
代码改了文档不会跟着动，而读者又完全信任它。`doc_audit` 因此对账端点、CLI 子命令、
`IDX_SCHEMA`、外观 token 与文档内的路径链接。

> **范围是路径规则，不是文件清单**：`doc_audit` 扫 `docs/**`，而对账范围认的是
> `reference/`。新增一份参考手册放进这个目录就自动进对账——不必记得去某张名单上登记，
> 而名单恰恰是最容易忘记维护的东西。

## methodology/ — 可迁移方法论（不进对账）

| 文档 | 什么时候看 |
|---|---|
| [问题域手册.md](methodology/问题域手册.md) | 想给别的 agent 工具（Codex / opencode / 自研）做同类分析器——九个能力单元，每个标注「换 harness 时哪些变、哪些不变」 |
| [报文解读.md](methodology/报文解读.md) | 想读懂 CC 的报文本身——9 种请求逐一解读 + 识别方法论 |

这两份讲的**不是「本项目怎么实现的」，而是「做这类工具会遇到什么」**。它们腐化风险最低，
分出来之后基本不用管——这是分层直接省下的维护量。

## 不在这里的两类

| 内容 | 在哪 | 为什么不在 docs/ |
|---|---|---|
| **项目叙事**（这软件怎么走到今天、当前状态、下一步） | [CHANGELOG](../CHANGELOG.md) 顶部速览 + 发版 tag | 它随进度变，属于流水而非手册 |
| **项目断面**（可重建规格：重新开发要做哪些功能、每个功能哪些细节点必须做对） | 本地 `sections/`，不进仓库 | 断面是冻结快照、内部治理视角；每份翻三语不可承受 |

**「项目叙事」曾经长在 `架构总览.md` 末尾**（演进主线 / 设计哲学 / 代码气质三节），260808 迁出。
迁出的理由不是它们写得不好，而是它们在别处已经有更合适的归宿，留在手册里只会分叉出第二份
副本——而副本从来只朝一个方向发展：过时。迁出时那三节里确实有一条已经说错了话
（写着「剩下的是跨天趋势」，而跨天趋势早就做完了）。
