# 三类文档与项目协作

2026-09-06 · 本地协作思考。文件分工与生成链已经落地；是否让人更容易理解项目、让 Agent 更稳定地执行，还需要在真实迭代中检验。

## 为什么要分成三个方向

这个项目持续迭代，参与者面对的问题不同：开发 Agent 要知道怎样修改项目；调用软件的 Agent 要知道怎样完成一次观测或分析；项目负责人需要理解项目、表达意图、判断结果，并决定下一步。

把这些信息混在一起，容易让一次需求变成常驻规则，让旧实现变成不能改变的目标，也让人为了作一个决定不得不读完整开发历史。因此，文档按任务分工，同一事实仍然只有一个维护位置。三个方向是三个入口，同一个 AI 也可以在不同任务中切换角色。

| 方向 | 首先回答什么 | 主要维护位置 | 读完应当能做什么 |
|---|---|---|---|
| 开发与接手 | 现在到哪了，怎么改才符合项目约束？ | CLAUDE.md、CHANGELOG、docs/development、相关 commit 与 issue | 在当前有效目标下修改并验证项目 |
| 软件使用 | 怎么调用这个工具，结果能说明什么？ | docs/usage，尤其 AI_USAGE 与 API 契约 | 完成操作、解释结果、处理异常与副作用 |
| 项目理解与决策 | 为什么做，现在怎样，这轮希望改变什么？ | docs/product、这本 HTML、当前 issue 与验收证据 | 形成判断、下发需求、纠正理解、决定下一轮 |

## 开发方向：按需披露有效上下文

`CLAUDE.md → CHANGELOG → commit → issue` 表达逐步深入的阅读路径。入口说明工作方式和资料位置，速览说明当前状态，相关提交和 issue 提供取证、方案、否决理由与验证过程。它不要求每次把所有历史读完；开发 Agent 应按当前任务补读安全、架构、接口或界面约定。

常驻入口应简短，稳定且反复适用的规则才进入开发约定；单次需求进入 issue。必要理由不能全藏进历史：读者需要知道某条约束防什么问题，才能正确应用它；完整演变则可以继续下钻。

要防止一种失误：Agent 严格遵守了文件，却执行了已经过期的项目理解。目标改变时，应同步修订受影响的当前需求和规则，明确哪些旧决定已被替代。代码可以证明当前实现，不能替负责人决定未来目标；文件较新或 issue 已关闭，也不能单独证明其中所有结论仍然有效。

## 使用方向：把软件当作可调用的工具

AI_USAGE 说明启动、发现实例、查询、分析、结果含义和副作用。API 契约提供精确的接口与字段定义。它们服务于“使用已有软件”，开发规则服务于“修改软件”；两者可以互相引用，不能互相代替。

使用 Agent 拿到的可能只有一个可执行文件，没有源码仓库。因此，随软件打包的 AI_USAGE 必须自足。为完成离线操作保留必要重复是合理的，不能把关键步骤删成指向仓库的链接。这本 HTML 可以解释其职责，不需要复制完整 AI_USAGE 才能成为统一阅读入口。

说明还要区分观测、推断和未确认事项：没有录到不等于没有发生，工具调用成功不等于用户目标达成。对会修改配置或数据的操作，应说明真实条件和副作用，不能把隔离测试时的条件写成普通运行的默认保证。

## 负责人方向：从理解到作决定

负责人入口需要连贯地回答五个问题：

1. **为什么做？** 面向谁，解决什么问题，哪些取舍仍然成立。
2. **现在怎样？** 已提供什么、有哪些限制、哪些仍是建议或实验。
3. **这轮改变什么？** 期望结果、范围、约束，以及暂不解决的部分。
4. **怎样判断做好？** 要看到哪些行为变化和证据，还有什么无法验证。
5. **下一轮怎么调整？** 接受结果、纠正理解、补充资源，或改变方向。

“最终事实”也需要前因后果。例如，单写“界面文字可以复制”，看不出功能服务于什么工作；说明“为了把诊断证据带到外部讨论，请求内容和错误信息应能直接复制”，就能据此评估设计是否合适。日常正文保留理解当前决定所需的原因，原始过程留在证据与历史中。

负责人控制的是目标、取舍和成功标准，也能调整 Agent 获得的资料、工具说明与约束。修改 CLAUDE.md 只是其中一种方式。既有授权范围内的工作仍可由 Agent 自主完成，不需要把这套文档分工变成每一步都等待人工批准的流程。

## 三个方向如何形成迭代闭环

**理解现状与证据 → 表达目标和取舍 → 整理成可执行需求 → 执行与验证 → 展示实际变化 → 决定下一轮。**

| 这次产生了什么信息 | 更新哪里 | 怎样避免分叉 |
|---|---|---|
| 新需求、范围或取舍 | 当前 issue；影响长期产品定义时更新 docs/product | 区分负责人决定、AI 建议和待确认问题 |
| 反复适用的开发约束 | 开发约定；入口只保留导航或本地特有规则 | 改原条目，并合并或撤销被替代的规则 |
| 操作步骤、接口语义变化 | docs/usage 的对应正文与消费侧 | AI_USAGE 的分发自足和 API 的精确定义各司其职 |
| 当前实现或完成状态变化 | CHANGELOG 速览与产品对应说明 | 实现完成、验证通过和用户验收分别表述 |
| 方案原因、失败尝试与验证结果 | issue、commit 与必要证据 | 当前正文提炼仍有效的判断，历史记录保留原过程 |

比如，Agent 反复读取同一文件，先记下具体运行与步骤，再提出原因假设。可能是入口不清、资料太长，也可能是文件发生变化、上下文压缩或正常复核。原因不同，修改位置也不同；不能直接得出“缺一条规则”的结论。

选择一个有依据的改进后，再用后续任务观察是否减少了同类卡点，同时确认结果质量没有下降。有效的改变才值得保留，失效或重复的约束需要合并、撤销。补资源和清理资源应当同时进行。

## 与我们对 Agent 的理解有什么联系

可以把 Agent 的工作看成从起点走向目标的一条生产过程：数据、文件、脚本、工具说明和 hooks 是它使用的材料与条件。要改进执行，既要看每一步做了什么，也要看它当时获得什么、缺少什么，以及结果如何被验证。

这也解释了 CCWA 的价值方向：把运行记录转成可核对的线索，帮助人判断该补充或修订什么。行为只能提供原因线索，不能直接证明模型的内部想法。现实任务的数据可能缺失、过时或冲突，错误的代价也不同；因此，资料质量、护栏与验证方式都属于需要建设的工作条件。

“看懂运行 → 找到有证据的缺口 → 改进资源或规则 → 再验证”是我们希望形成的闭环。当前文件重构为这个闭环提供了基础，尚不代表自动诊断、自动修订或协作收益已经得到证明。

## HTML、源文件与公开披露的边界

HTML 是便于人理解、展开和追问的阅读载体。产品资料和 Markdown 是编辑源，构建把它们汇成一本书；不直接修改生成 HTML，也不让它成为另一份需要人工同步的事实副本。本文是思路说明，执行规则仍以当前 CLAUDE.md 和开发约定为准，单次决定以对应 issue 为准。

现阶段公开内容集中在 `public/`，保留重构开始时的披露断面，不参与日常需求与规则更新。本地工作先把三个方向用顺，再讨论公开内容如何更新；当前不增加同步、推送或发布流程。

这套逻辑是否有用，应从真实迭代中判断：人能否说明项目当前目标和限制，Agent 能否找到正确资料，旧决定是否被及时替换，结论能否回到证据，以及新规则是否真的减少了同类问题。文件分好目录只是开始。
