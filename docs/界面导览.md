# CC Wire Analyzer 界面导览

> 读者：用 CC Wire Analyzer 审计自己 Claude Code 流量的人类用户（包括非程序员）。
> 配套：[API契约.md](API契约.md)（接口规格，给前端/agent）、[AI_USAGE.md](AI_USAGE.md)（AI agent 入门）。
> 本篇专写**人看到什么、数据从哪来、能从这里看出 CC 在干什么**——把冰山水下部分抬上来。
> 本篇只讲「怎么用」，不列开发待办——待办的真源是 [CHANGELOG.md](../CHANGELOG.md) 顶部速览的
> 「下一步」，开发约定见 [开发指南.md](开发指南.md)。

## 引子：你看到的只是冰山一角

CC Wire Analyzer 透明录制了 Claude Code 与上游端点的每一次 HTTP 对话——
请求体里的 system prompt 原始水印、SSE 分块时序、安全分类器调用、精确 token 成本，全部躺在
`~/.cc-wire-analyzer/captures/*.jsonl` 里。但打开 app，你看到的捕获列表 + 时序 DAG 只是其中
一小部分。

> **后端已经算出来、UI 却完全没入口的能力**：失败聚合（`/api/diagnose/errors`）把一天几千条
> 失败压缩成几句人话，但前端代码 `grep diagnose` 是 0 命中——这是项目自己承认的最大缺口。

这不是文档疏漏，而是**功能优先级留下的洞**：项目先服务 AI agent（agent 走 CLI/API 能拿到全部
诊断原料），人类 UI 还停在"列表 + DAG + 详情"三件套。本文档把现状摸清楚——**包括哪些能力
在 UI 里根本没有入口**，那正是你需要转去 CLI/API 的地方。

## 核心概念（先认术语，后面不再解释）

CC Wire Analyzer 的 UI 围绕几个 CC 内部概念组织，第一次接触会撞墙——这里一次性定义清楚。

| 术语 | 中文叫法 | 是什么 |
|------|---------|--------|
| **record** | 录制 | 一次 HTTP 请求+响应的完整快照（请求头/体、响应聚合、错误信息）。每条有 `id`（形如 `req_a1b2c3d`）|
| **idx** | 索引 | 同一条 record 的轻量摘要（1-2KB vs record 可超 5MB），UI 列表/DAG 都只读索引 |
| **session** | 会话 | 一次 CC 启动对应一个会话 id（`X-Claude-Code-Session-Id` 头）；与 `~/.claude/projects/` 下 jsonl 文件名一致 |
| **lane**（泳道）| 时序 DAG 的纵列 | 同一会话的请求归一条主线泳道；子代理各占一条实例泳道；辅助调用合一条 |
| **kind** | 请求的语义角色 | 7 种：`main`（主线对话）/ `subagent`（子代理）/ `title`（标题生成）/ `compact`（压缩）/ `security`（安全扫描）/ `count_tokens`（上下文估算探针）/ `other`。每种 kind 的报文形态与识别方法见 [报文解读.md](报文解读.md) |
| **turn_start** | 轮次起点 | 用户发了一条新消息（非工具回传）触发的那次请求 |
| **pure_chat** | 纯对话轮 | 整轮零 tool_use——你只是问了个问题、AI 答了，没动手 |
| **ttft** | 首 token 时间 | Time To First Token，从请求发出到上游吐第一个字的毫秒数 |
| **trigger 边** | 派生触发线 | 主线响应里调用了 Task/Agent 工具 → 派生子代理 → DAG 上画一条主线到子代理的虚线 |
| **effort** | 努力档位 | CC 的 reasoning effort（low/high/max），决定模型思考多久 |
| **thinking** | 思考模式 | enabled/disabled/adaptive，与 effort 联合决定官方端点是否接受请求 |

## 第一层：四个视图各是什么

CC Wire Analyzer 的 tab 栏只有 3 个按钮（捕获 / 时序 / 设置），但实际有 **4 个视图**——详情是
次级视图，没有独立 tab，从列表或 DAG 节点点击进入。

### 1.1 捕获列表（默认视图）

**这是 app 打开后看到的第一屏**，列表展示当日所有 HTTP 请求，倒序排列（最新在最前）。

#### 你看到什么

每行 10 列信息：时间 / 状态色点 / 方法+路径 / kind chip（main 行不显）/ 模型 / 耗时 / token /
ttft / 摘要 / 判定 chip（仅安全审查行）。**列宽固定、逐行对齐**（260730 改 CSS grid：此前是
flex，kind chip 有无与模型名长短会推动后面所有列，实测摘要列起点在 13 行里漂 300px）。路径与
模型名过长时截断，完整值挂在 `title` 上（悬停可看）。

顶部一张状态卡显示代理状态、路由（`listen → upstream`）、今日计数。状态卡下面可能叠加多条
告警横幅（cc-switch 警告 / 外部接管 / 孤儿恢复 / 落盘失败 / 体检 error/warning）。

日期行右侧（与"清理"并列的工具区）有一个**失败聚合按钮**：`● 失败 N · M 组`，
**当天没有失败时不渲染**。点它在日期行下方就地展开面板，每组一张卡：

- 头部：`×次数` + 错误类型 + HTTP 状态 + 受影响的请求类型（`主线×19` / `标题×19`…）
- 中部：**上游自己给出的错误原文**——这是整块面板的重点，上游已经替你诊断过一次
- 请求侧字段：`effort=max` / `model=[glm-5.2, glm-5v-turbo]` 这样的小胶囊。
  **加粗的是"全组一致"（可能就是病因），方括号列表是"跨多个值"（可以排除这个字段）**
- 底部：起止时间、涉及几个会话、样本 id（点一下直接跳到那条的详情）

一天几千条失败会被压成几组人话——实测 2719 条 → 7 组、0.09 秒。这块的价值不在"看到有失败"
（列表里的红点已经说了），而在**看出这些失败其实是同一个原因**。

> **它为什么是个小按钮，不是横幅**：260801 首版把它做成状态卡下方的整宽横幅，当天就降级了。
> 它是**归纳**不是**告警**——真告警说的是"现在有件事正在坏"（录制没落盘、代理被绕过），
> 不看会损失数据；失败聚合是查问题时才要的分析视角，平时不看没有损失。把归纳摆成告警的位置，
> 既占掉主内容的首屏高度，又会**稀释真告警的分量**：一个天天都在的横幅，人第三天就不看了，
> 那条"落盘失败"的红条会跟着一起被无视。同 2.2 节体检铁律里那句"第二次误报之后横幅就再没人看"。

#### 数据从哪来

- 列表数据：`GET /api/captures?date=YYYY-MM-DD` → 返回 `{date, total, items[], dates_available}`
- 每个 item 是 idx 摘要（剥离了 DAG 分类原料等私有字段）
- 状态卡：`GET /api/proxy/status`（5 秒轮询）+ `GET /api/health/config`（体检）
- 失败聚合：`GET /api/diagnose/errors?date=…&limit=50`（切日期时取一次；LIVE 期间只在**新到的
  增量里确实有失败**时才防抖重取，否则一天几千条成功流量会把它变成 800ms 一次的全量扫描）
- 实时增量：`GET /api/captures/stream`（SSE，新请求或请求完成时推摘要）

#### 反思：信息密度对人不友好

> 一行塞 10 列等宽字体多色 chip，对工程师是信息密度，对非工程师是噪音。
> 尤其是 token 列 `1.2k→800 (+1.5k cache)`——cache_read 是什么、为什么这么高，没有解释。

但**状态卡做得很对**：`http://127.0.0.1:5051 → https://...` 的端到端路由让人一眼看到代理正在
转发到哪。这是审计的基本盘。

#### 容易踩的坑

- **清理按钮二次确认是 4 秒倒计时**：第一次点展开下拉菜单，选"清除"后按钮变红脉冲 4 秒，
  在窗口期内再点才执行；分神就以为"点了没反应"。这是防误删的设计，但缺乏提示。
- **告警横幅只在捕获 tab 可见**：DOM 全在 `view-list` section 内，切到设置/时序就隐藏。
  打开设置时其实也跑了一次体检（refreshHealth），但切过去看不到结果——见下面 1.4。

### 1.2 详情视图（无独立 tab）

**点列表任一行进入**，左右两栏 grid 展开单条 record 的完整请求与响应。

#### 你看到什么

顶部面包屑是两栏共用的：id + method+path + 状态 chip + timing（起止/total/ttft）。两栏各自
以「栏头 + 元信息卡」开场，且**两栏的元信息卡等高**——下面每一块因此左右齐平（260730 修：请求侧
原先是个裸 chip 行，比对面的卡片矮 27px，两栏从第二块起全程错开）。

- 左栏（请求）：元信息卡（model / stream，均来自请求体）→ 安全审查卡（仅 security 请求）
  → 折叠的 Headers → 折叠的 System blocks（每块标注角色）→ 折叠的 Tools → 默认展开但只显
  最近 3 条的 Messages
- 右栏（响应）：元信息卡（status / stop_reason / ttft / total，均为响应侧字段）→ 默认展开的
  响应 Headers（wire-only 字段高亮）→ Usage 四宫格（input/output/cache_read/cache_creation，
  只给原始 token 数，**不折算金额**）→ Content Blocks（thinking/text/tool_use 分段显示）
- 失败时多了 Error dcard（kind/status/detail/body_snippet）

> `model` / `stream` 在请求侧不是笔误：它们是请求体里 CC 指定的参数，本工具**不记录响应侧的
> model 字段**（实测上游未回）。成本估算已在 v0.4.1 删除——按刊例折算对走第三方网关的用户不准。

#### 数据从哪来

`GET /api/captures/<rid>?date=YYYY-MM-DD` → 完整 record（含 request.body 的 system/tools/
messages，response.content_blocks 全量）。底层用 idx 的字节偏移直接 seek 到主文件对应位置。

#### 反思：响应头曾默认折叠藏起最值钱的信息（v0.4.0 已修）

> 响应 Headers 区域的代码注释作者自己写道：「这里恰恰是 wire 层最值钱的信息：
> anthropic-ratelimit-*（限流余量）、request-id（找上游对账）」。

`anthropic-ratelimit-tokens-remaining` 能告诉你"还剩多少额度"，`request-id` 是上游对账的钥匙。
这些字段只在 wire 层看得到（CC 自己的 jsonl 不记录响应头），是本工具相对 jsonl 的核心增量。

**v0.4.0 改动**：响应 Headers 面板已**默认展开**，wire 层独有字段（`anthropic-ratelimit-*` /
`request-id` / `anthropic-organization-id` / `x-should-retry`）以**加粗 + 品牌色高亮**，并附
提示"仅在 wire 层可见，CC jsonl 不记录"。原先的折叠状态让新手不知道这里有金矿——现在默认摊开。

#### 每段大文本的工具条

每段长文本（system block / message / content block）右上角有一组工具按钮：展开 / 复制 /
格式化（JSON 美化或 markdown 渲染）/ **翻译**（调 `/api/translate` SSE 流式）/ **AI 解读**
（调 `/api/explain`，带防注入隔离）。

翻译与解读的结果块顶部可能出现一条金色提示，说明**这次输出为什么到此为止**（260801）：

| 提示 | 含义 | 调大「最大输出 tokens」有用吗 |
|---|---|---|
| 原文过长，只发送了前 20000 字符 | 本工具在发出去之前砍的（成本护栏） | ❌ 砍的是输入，与输出上限无关 |
| 输出到达上限被截断（当前设置 N） | 上游 `finish_reason=length` | 也许——上游模型自身也有输出上限，填得再大也超不过它 |
| 上游内容审查中断了输出 | 上游 `finish_reason=content_filter` | ❌ |

没有这条提示 = 模型自然说完了。此前三种成因在界面上长得一模一样（都是文本停在半截），
用户改了设置也无从判断有没有生效。

> 复制功能背后是一段隐形工程：因为 WebView2 把原生右键菜单绑在 debug 开关、macOS WebKit
> 干脆没 Edit 菜单，复制链路全靠前端自绘右键菜单兜底。260801 起正文默认可选（只有按钮 /
> 标签页 / DAG 节点这类交互控件不可选），此前是反过来的白名单，导致详情页的 `req_xxxxxx`、
> 设置页的路径等一批只读文本选不中也拷不走——这是开发者门槛，对最终用户透明。

### 1.3 时序 DAG（核心可视化）

**这是项目最复杂的视图**，画一张时序有向图：纵轴是泳道（分组），横轴是时间。

#### 你看到什么

- **节点**（dag-node）：一条 HTTP 请求。卡内：时间 / kind chip / 模型 / 耗时 / token / 摘要。
  安全审查节点的摘要显示「审查：<待判定动作>」（与列表行同一套格式化，260730 补——此前显示的是
  响应正文残片 `<severity>8`、`<block>yes</block><category>…`，即所有可选摘要里最没信息量的那段）
- **泳道头**：lane 颜色 + 名称（主线 N）+ 计数 + 短码
- **泳道配色**（260801 起）：主线按首见顺序取六色色板；**子代理 = 派生方同色混白淡化**，
  嵌套派生（子代理再派生子代理）逐级更浅，同族一眼可辨；派生方没录到的子代理
  （Workflow 派生无 trigger 边）保持蓝色——蓝色的含义是「派生方不在图上」
- **三种连线**：
  - **seq**（同 lane 实线）：同一泳道里前后相邻的请求
  - **trigger**（粗虚线带箭头）：主线派生了子代理
  - **near**（点线）：辅助调用挂到时序最近的主线
- **三档节点视觉**：默认卡片=轮次起点 / mid 细条=工具循环步 / chat 虚线带💬=纯对话轮
- **错误折叠**：连续 ≥2 个错误节点折叠成 "ERR RUN ×N" 红卡，点击展开

#### 数据从哪来

`GET /api/dag?date=YYYY-MM-DD` → `{nodes[], edges[], lanes[]}`。后端 `classifier.build_dag`
从索引记录构建：
- 每个 node 含 kind/lane/turn_start/tool_uses/pure_chat 等分层原料
- lane 含 kind/main|subagent|aux/count/session_id
- edge 含 from/to/type

#### 反思：派生关系画了线但没画"派生什么"

> DAG 上的 trigger 边（粗虚线带箭头）告诉你"主线 N 派生了某个子代理"，但子代理节点上
> **没有可读标签告诉你派生 prompt 是什么**。后端 `task_prompts` 字段已经算好了——
> 主线响应里 Task/Agent 工具的 input.prompt 全文都存在，子代理首条 user 也对齐了——
> 但 UI 没渲染。你看到 5 个 Explore 子代理，却不知道各自被派生去做什么任务。

这是 UI 与后端能力之间最宽的一道缝——数据齐了，界面没接。

#### 泳道头的短码语义

主线泳道头 **v0.4.0 起显示"主线 N"序号**（按首见时间排 1, 2, 3…），副标签才显示 `session_id`
前 8 位 hex 短码（能对上 `~/.claude/projects/` 下的 jsonl 文件名）。子代理/辅助泳道头仍显示
`lane_id` 前 8 位（md5 短码）——md5 对人无意义，"派生自主线 N + 可点击查看 prompt"仍是待办。

#### 交互细节

- **hover 节点无 tooltip**（只有派生关系的 assoc-dot 圆点带 title）——为什么这卡是金色、
  为什么连这条虚线，全靠图例+颜色推断
- **泳道下拉**：可勾选/取消显示某条泳道，隐藏后剩余泳道自动适应宽度变大。
  **关闭是级联的**（260801 起）：关一条主线会连同它派生的子代理（含嵌套）与关联辅助调用
  一起隐藏，下拉里这些行标注「随 XX 隐藏」；想单独看某个子代理，再勾它一下就单独显示
  （父级仍藏）。重新打开主线后，没被单独关过的子代理全部恢复
- **隐藏 mid / 隐藏 aux 两个 toggle**：把工具循环步或辅助调用藏掉，聚焦主线
- **LIVE 重绘**：800ms 防抖，节点数或泳道数变化时回退全量重渲

### 1.4 设置（4 张卡 + 保存）

**界面 / 代理与数据 / LLM 模型 / 给 AI 用 / 关于** 五张卡同列纵向排，底部一个保存按钮。

#### 你看到什么

- **界面**：语言下拉（中/英/日，立即生效）+ **缩放下拉**（90%~200%，260801 加，立即生效并保存）。
  高分辨率屏（2K/4K，系统缩放 100%）觉得字小就调大——全部 CSS 是绝对 px，此前只能去改系统缩放
- **代理与数据**：settings.json 路径（只读）、当前 BASE_URL（只读）、备份目录（带"打开"按钮）、
  自动启动代理 toggle、保留天数 input
- **LLM 模型**：API Key（密码+眼睛切换）/ Base URL / Model / Temperature / Max tokens /
  翻译目标语言 / AI 解读提示词 textarea / 测试连通按钮
- **给 AI 用**（260801）：一句可复制的话（含本机实际端口）、说明书端点地址、无界面模式命令。
  把那句话粘给你自己的 AI，它就能读到完整用法并驱动本工具——**不需要这个仓库**，
  说明书打包在产物里
- **关于**：版本 / 数据目录 / 日志路径

#### 数据从哪来

- 读：`GET /api/config` + `GET /api/about` + `GET /api/proxy/status`
- 写：`POST /api/config`（白名单合并）
- 测试连通：`POST /api/translate/test`（先 saveConfig 再 ping）
- 打开备份目录：`POST /api/open-folder`（仅允许 CONFIG_DIR 内）

#### 反思：曾经的"三个死配置"前端层都已修复

| 配置 | 旧描述 | 实际状态 |
|------|------------------|----------|
| `redact_headers` | 死配置（UI 承诺可关闭脱敏、代码无条件调用） | **UI 字段已删**，脱敏恒开 |
| `auto_start_proxy` | 死配置 | **前端已接线**（init 时检测并触发 toggleProxy）|
| `retention_days` | 死配置 | 前端保存送后端，但**完整闭环需另查后端 `enforce_retention`**|

三个配置 260713 已全部修复（前两个接线、第三个连同 UI 开关一起删除），现作为历史参考保留在
[开发指南.md](开发指南.md) 的惯犯 bug ①里——**记的是这类 bug 会再产，不是当前 bug 清单**。

#### 反思：体检在设置 tab 隐身

打开设置 tab 时顺手跑了一次 `refreshHealth()`（前端代码有），但**体检横幅和抽屉的 DOM 全在
`view-list` section 内**——切到设置 tab 后，体检结果完全看不到。用户改完配置想立刻看体检
反馈，必须切回捕获 tab。这是反直觉的。

## 第二层：藏在 UI 之外的关键能力

这一层是本文档最重要的部分——**项目已经算出来但 UI 完全没暴露的诊断能力**。
读懂这一层，你才能用对工具。

### 2.1 失败聚合（diagnose）：260801 起 UI 有入口，语义仍值得先读一遍

> **这是一天里几千条失败压缩成几句人话的能力**：把 `(err_kind, status, 错误消息指纹)`
> 相同的失败归一组，每组摆出请求侧字段（model/effort/thinking/stream/max_tokens）。
> 一次实测把 2719 条失败归并成 7 组，0.09 秒完成。

每一组的样子：

```
err_kind: upstream_4xx
status:   400
message:  effort 'max' is not supported when thinking is disabled
count:    19
first_ts: 2026-07-18 10:22:01
last_ts:  2026-07-18 16:14:33
kinds:    {title: 19}              ← 全是标题生成请求
sessions: 1
req_fields:
  effort:    max                   ← 单值：全组都是 max（可能病因）
  thinking:  disabled              ← 单值：全组都是 disabled（可能病因）
  model:     [glm-5.2, glm-5v-turbo]   ← 列表：跨多种模型出现（排除模型当因）
```

`req_fields` 单值/列表语义是这套设计的精髓：

- **单值** = 全组在这字段上完全一致 → **可能是病因**
- **列表** = 跨多种值都出现 → **排除了这个字段当因**

光看 `message: effort 'max' is not supported when thinking is disabled` 加 `req_fields:
effort=max + thinking=disabled`，病因一目了然——比你逐条点开 19 个红卡看错误快几个数量级。

#### 怎么访问

```bash
# 界面（260801 起）：捕获页状态卡下方的「本日失败 N 条 → 归并为 M 组」折叠区

# CLI（给 agent 用，但人也能跑）
uv run python src/cli.py errors
uv run python src/cli.py errors --date 2026-07-18 --limit 50

# API
curl "http://127.0.0.1:<port>/api/diagnose/errors?date=2026-07-18"
```

#### 这道缝曾经最宽，值得记住它为什么会存在

后端把一天几千条失败压成 7 组只要 0.09 秒，而**这个结论有整整六周没送到人眼前**——算力早就
花掉了，只是没人给它接一个入口。这不是难度问题（前端约 200 行、后端零改动），而是
"能力做完了就以为交付完了"的典型：**一个只有 API 能看到的结论，对不会调 API 的用户等于不存在。**
260801 补上入口后，这条经验留在这里，是为了下次再出现"后端算好了、界面没接"时能早一点认出来。

### 2.2 配置体检（doctor）：入口隐蔽 + 跨 tab 隐身

8 条只读规则，启动代理前跑一遍，error 级拦启动（留 `force=1` 逃生门）。

| # | code | severity | 检查什么（一句话） |
|---|------|----------|----------|
| 1 | `half_switch_to_subscription` | error | BASE_URL 指第三方但没 token，OAuth 却在 → 切了一半 |
| 2 | `dead_port_leftover` | error | BASE_URL 指本机端口但没人听 → 代理死了/残留 |
| 3 | `self_reference_state` | error | BASE_URL 指本实例端口但不在 patch 态 → 会自指递归 |
| 4 | `oauth_expired` | error | OAuth 过期 + 用订阅模式 → 会 401 |
| 5 | `effort_level_conflict` | warning | 顶层 effortLevel 与 env 矛盾 → 顶层那个无效 |
| 6 | `effort_max_rejected_upstream` | warning | effort=max + 官方端点 → 标题生成等静默 400 |
| 7 | `oauth_expiring_soon` | info | OAuth 还剩 < 1 小时过期 |
| 8 | `token_overrides_oauth` | info | 同时有 OAuth 和 token → token 优先（多半你故意的）|

> **自检**：加/改 doctor 规则必须同步 `src/doctor.py` 的 `check()` 规则元组（真源）+ `dc.*`/`dcfix.*` 三语 i18n + 本表，三处缺一就是惯犯 bug ③。

#### 入口隐蔽在哪

- **没有独立 tab**：体检结果通过捕获 tab 顶部的横幅 + 抽屉展示
- **error 级有红横幅**，warning 级有黄横幅，**info 级只进抽屉**（无横幅提示）
- **抽屉默认收起**，需点"查看详情"展开
- **打开设置时虽然跑了体检但 DOM 在 captures section**——切过去看不到（见 1.4 反思）
- **i18n 已覆盖全部 8 条规则**（`dc.*` 三语 zh/en/ja，v0.4.0 补齐）；不再回落英文 code

#### 反思：体检结论还有几个隐藏字段

`/api/health/config` 返回的不止 `issues[]`，还有：
- `intent`（subscription/third_party/unknown）：体检认为你想用哪种认证方式——**UI 从未显示**
- `scope` + `scope_note`：体检读的是 settings.json 文件，不是 CC 进程环境——**UI 从未显示**
  （这条边界很重要：你改了 settings.json 但 CC 没重启，体检看到的还是旧值）

### 2.3 派生关系（trigger 边 + task_prompts）：画了线没画内容

DAG 上 trigger 边告诉你"主线 N 派生了某个子代理"，但**派生 prompt 全文藏起来了**：

- `idx.task_prompts`：主线响应里每个 Task/Agent 工具的 input.prompt（前 1000 字）——**UI 不显示**
- `idx.first_user_task`：子代理首条 user 剥掉 `<system-reminder>` 后的前 1500 字（≈派生 prompt 原文）
  ——**UI 不显示**

结果：你看到 DAG 上有 5 个子代理节点，但要知道它们各自被派生去做什么任务，必须点进每条详情
自己翻 messages[0]。

靠 task_prompts 对齐判别子代理实例 lane 的逻辑曾有 bug——**并行派生 + 同类型 agent + 模板化
prompt** 的组合会让多个子代理挤到一条泳道上。**v0.4.0 已修复**（`PROMPT_PROBE_LEN` 120→300、
`PROMPT_MATCH_LEN` 200→1000、实例键改 `{mid}|{p[:1000]}`，`IDX_SCHEMA` 3→4 触发旧索引重建），
仅剩"前 300 字仍完全相同"的边界情形留待双向匹配策略。但 task_prompts 在 UI 仍不可见——如果
可见，用户能一眼看出剩余的撞车边界情形。

### 2.4 响应头：wire 层最值钱的字段（v0.4.0 起默认展开 + 加粗）

详情视图的"响应 Headers"区域 **v0.4.0 起默认展开**，wire 层独有的关键字段（`anthropic-ratelimit-*` /
`request-id` / `anthropic-organization-id` / `x-should-retry`）以**加粗 + 品牌色高亮**，并附提示
"仅在 wire 层可见，CC jsonl 不记录"。这些是 CC jsonl 永远记录不到的字段：

| 响应头 | 含义 | 审计价值 |
|--------|------|----------|
| `anthropic-ratelimit-tokens-remaining` | 还剩多少 token 额度 | 提前知道会不会撞限流 |
| `anthropic-ratelimit-requests-remaining` | 还剩多少次请求额度 | 同上 |
| `request-id` | 上游分配的请求 id | 跟上游对账/报 bug 时用 |
| `anthropic-organization-id` | 你所属的组织 id | 验证用的是哪个账号 |

代码注释作者自己写道："这里恰恰是 wire 层最值钱的信息"——原先默认折叠让新手不知道，现已摊开。

### 2.5 子代理身份判别信号：完全在 UI 之外

决定一条请求是不是子代理、属于哪条实例泳道的核心信号：

- `is_subagent`：system block[0] 计费头的 `cc_is_subagent=true`（**权威位**，260725 实测确立）
- `entrypoint`：`cc_entrypoint`（cli/sdk-cli/sdk-mcp，区分交互 vs headless vs MCP）
- `agent_fp`：system block[2] 的 md5（区分 Explore/Plan/general-purpose）
- `session_id`：CC 会话 id（子代理复用父的，只能当 lane 键）

这些字段全在 idx 里、API 也返回，但 **UI 完全不显示**。当泳道判别出问题时（比如本次撞车
bug），用户只能用 `tools/lane_probe.py` 才能摊开看——非程序员根本无从下手。

## 收束：界面之外还有一半

把这篇读完，你会发现 UI 只是这个工具的一半。

> 后端把失败聚合、体检结论、派生关系、响应头 ratelimit 全都算好摆在那儿了，但**它们不都有
> UI 入口**——上面「第二层」列的每一条，都是「数据已经在盘上、界面还没接上」。

这不是缺陷说明，是使用建议：**当界面回答不了你的问题时，别以为工具没录**。附录 A 的对照表
标了每个术语在哪能看到，标着 ❌ 的那几行就是转去 CLI / HTTP API 的信号——
[AI_USAGE.md](AI_USAGE.md) 有完整命令，附录 B 有端点速查。

你手上这份录制里躺着 CC 替你做的每一件事，包括它没告诉你的那些。看不看得见，取决于你从哪个
口子进去。
