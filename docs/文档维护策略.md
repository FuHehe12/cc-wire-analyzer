## 引子：文档腐化是指数级的

> **功能增长是线性以上的，文档腐化是指数级的**——每加一个功能，旧文档都要被重读、判断是否
> 需要改、改对地方。任何一个环节漏掉，文档就和代码分叉，下次读者（人或 AI）就被误导。

这不是假设——cc-wire-analyzer 当前已经有具体证据。下面三处腐化都是 260725 多视角扒查时**实际
发现**的，不是文档自检发现的：

| 文档 | 腐化表现 | 怎么发现的 |
|------|---------|----------|
| `docs/API契约.md` | 缺 `/api/health/config` 和 `/api/diagnose/errors` 两个新端点；`usage` 字段名双轨（契约写短名，实际录的是 Anthropic 全名） | 后端 API 子代理扒查 |
| `CLAUDE.md` 的「死配置」段 | 描述滞后——`redact_headers` UI 已删、`auto_start_proxy` 前端已接线，不再是死配置 | 前端子代理扒查 |
| `CLAUDE.md` 的验证清单 | 写了 `uv run python src/settings_guard_selftest.py`，但文件**不存在**——自测嵌在 `settings_guard.py --self-test` 里 | 外壳子代理扒查 |

注意一个规律：**腐化都是子代理扒查实际代码时发现的，项目目前没有"文档对账"机制**。等读者
撞上时已经晚了一步——这就是为什么需要这套策略。

## 适合本项目的策略

cc-wire-analyzer 是**单人维护 + AI 辅助 + 开源 + 多语言读者**的项目。最致命的失败模式是
**单人维护断裂**——维护者一旦忘了一个细节，没人补位，文档就分叉。所以策略应该往**让 AI 能
自检**那端倾斜，而不是模仿企业级 docs-as-code 方案。

### 策略一：SSOT 单一真源（最重要）

> **每个事实只在一处定义，其他地方引用**。文档之间互相矛盾就是文档无 SSOT 的后果——
> cc-wire-analyzer 已经有现成证据：契约说 `usage` 字段短名，AI_USAGE 说全名，代码里归一后
> 才短名。三处定义，三处真值。

代码里项目已经在做 SSOT（`usage_norm` 单一真源、`IDX_SCHEMA` 版本号），但**文档没有 SSOT
机制**。要做的是：

- **每个枚举/字段名/规则 code 只在一处权威定义**。候选位置：模块开头 docstring 或专门的
  `docs/字段字典.md`。其他文档提到这个字段时**链接过去**，不重复写定义。
- **每次字段集变化，SSOT 处定义、其他文档引用**。这跟代码里 `IDX_SCHEMA` bump 是同一种
  哲学——一处变，处处对得上。

具体落地：

| 真源类型 | 当前散落处 | 应集中的位置 |
|---------|-----------|-------------|
| API 端点列表 | API契约 + AI_USAGE + 界面导览 | `API契约.md` 唯一定义，其他文档引用 |
| kind 枚举 | classifier.py docstring + AI_USAGE + 界面导览 | classifier.py docstring 是 SSOT，文档引用 |
| err_kind 枚举 | proxy.py + diagnose.py + API契约 | proxy.py 各 `error.kind` 赋值点（:138/:144/:150/:240）是 SSOT；架构总览 §1.1 有异常→kind 映射表 |
| doctor 8 条规则 code | doctor.py + 界面导览 | doctor.py 的 `_r_*` 规则函数（见 `check()` 规则元组 :159-160）是 SSOT |
| 字段名（usage 短名 vs 全名） | 契约说短名、AI_USAGE 说全名、代码归一后才短名 | 统一为"录制格式=全名、API 出参=归一后短名"，在 SSOT 处显式说清 |
| **开发约定**（不变量 / 惯犯 bug / 自测 / 前端规则） | ~~CLAUDE.md + CONTRIBUTING + 架构总览**三处**~~ | `docs/开发指南.md` 唯一定义，另两处改引用（260729 落地，见腐化 #13/#14）|
| **HTTP 端点** | ~~API契约 + AI_USAGE + app.py 回落表~~ | `docs/API契约.md` 唯一**规格**定义（`tools/doc_audit.py` 机器对账）；AI_USAGE / 回落表只放速查一行 |
| **CLI 子命令** | ~~哪儿都没有~~（17 个子命令，公开文档零清单，260802 发现）| `docs/AI_USAGE.md` 的 CLI 表；`--help` 是参数权威，表里只讲"做什么 + 有没有副作用" |
| **beta 基线 `KNOWN_BETAS`** | ~~index.html 硬编码~~ | `classifier.KNOWN_BETAS`，前端由模板注入消费（260802 上提） |
| **索引 schema 当前值** | ~~架构总览写死 `= 10`，代码已 14~~ | `classifier.IDX_SCHEMA` 常量（旁带逐版注释），文档只讲机制不抄数字 |

> **自检**：新增一类真源（新枚举/新规则集）时必须在此表登记真源位置——这张表当年就漏掉"约定型真源"（见腐化 #13/#14）。登记时确认该位置真实含有可读的完整定义（以 `classifier.py` 的 `KIND_ORDER` 为范例：常量旁带 v1→v5 演进注释），别指了个空。

### 策略二：三层结构（导航 / 参考面 / 价值层）

避免单一大 README（越长越没人读）和功能文档矩阵（碎片化、引用腐烂）两个极端，按层级组织：

```
导航层（README）：项目门面 + Quick start + 链接
   │
   ▼
参考面（API契约 / 字段字典）：规格，机器可校验
   │
   ▼
价值层（界面导览 / 架构总览 / AI_USAGE）：叙事，按受众分
```

| 层 | 文档 | 写什么 | 何时更新 |
|----|------|--------|----------|
| 导航 | README.md（三语） | 一句话定位 + Quick start + 链接到价值层 | 加新功能时改 Quick start |
| 参考 | API契约.md / 字段字典 | 接口规格 / 枚举值 / 字段定义 | API/字段变化时必改（CI 校验） |
| 价值 | 界面导览 / 架构总览 / AI_USAGE | 按**受众**讲为什么和怎么用 | 受众视角有大变化时改 |

**价值层按受众分**，不按功能分。当前已有：
- 给人：`界面导览.md`（界面看什么）/ `报文解读.md`（CC 的 9 种请求报文是什么）
- 给开发者/复盘者：`架构总览.md`（怎么搭的）/ `开发指南.md`（改的时候不能破什么）
- 给 AI agent：`AI_USAGE.md`
- 给未来的同类项目：`问题域手册.md`（换 harness 时哪些结论还成立）

**260729 补一条判据：受众相同也要按「触发时机」分开。** 架构总览和开发指南读者都是开发者，
但一个是"我要读懂这个项目"、一个是"我正要动手改"——合在一份里，动手的人得翻过几百行架构叙事
才找到不变量清单。四份开发向文档的触发时机是：读懂→架构总览 / 动手→开发指南 / 改文档→本篇 /
做同类项目→问题域手册。

**新增功能时不要急着开新文档**——先想这个功能的读者是谁，归到现有受众文档里。比如失败聚合
加 UI 入口后，应该更新到 `界面导览.md` 的"第二层"段，而不是单开"失败聚合功能文档"。

### 策略三：每份文档自带"自检句"

在每个模块/功能文档的对应章节末尾写一句**给未来 AI/人的提示**：

> 如果你改了 X，必须同步改这里。

这是给未来维护者的提示，比 CI 校验更柔但覆盖更广（CI 校验得了链接和端点，校验不了语义）。

例：

- `docs/API契约.md` 的 `/api/proxy/status` 段末尾：「**自检**：加新字段时必须同步更新
  `_proxy_state()` 函数 + 此契约 + AI_USAGE 的字段表。」
- `docs/界面导览.md` 的视图章节末尾：「**自检**：加新视图/新横幅时必须更新此章节的视图清单
  + [架构总览.md] 的'第三层：交互'段。」
- `docs/开发指南.md` 的惯犯 bug ① 末尾：「**自检**：加新配置项时必须确认它在前端、后端
  `config.py`、实际消费点三处都接通——任何一处断了就是新的死配置。」

### 策略四：issue 先行扩展到文档同步

cc-wire-analyzer 已经有"改代码先开 issue"的纪律（**定义在 [开发指南.md](开发指南.md) 第八节**，
本篇不重复；本地的目录结构与路径细节在 `CLAUDE.md`，不上传开源仓库）。本篇只加文档相关的这一条：

> **任何带新功能/新字段的 issue，必须开"文档同步" sub-task**。issue closed 时核对该功能
> 涉及的所有文档提及处。

具体执行：

1. 开 issue 时在「产出」段列出"涉及的文档"清单（README / API契约 / 界面导览 / 架构总览 /
   AI_USAGE / 开发指南 / 问题域手册 / CLAUDE.md，按需勾选）
2. 改代码同时改文档（同一个 PR / 同一次本地改动）
3. close issue 前回读"自检句"，确认每处都同步

这与"issue 是迭代经历"的现有定位同源——文档同步也是迭代经历的一部分。

### 策略五：AI 可自检（项目特有的杠杆）

cc-wire-analyzer 的定位是"不只给人看，AI 也能自己开、自己查"。文档也应该让 AI 能自检。具体
做法：

- **结构化字段优先**：API/字段/规则用 markdown 表格（机器可解析），叙事用散文（人可读）。
- **`tools/doc_audit.py`（260802 已落地）**：对账六项机器可判定的事实——端点是否进了
  `API契约.md`（策略一指定的端点真源，"某份文档提过"不算）、CLI 子命令是否有文档、文档指向的
  仓库文件是否存在、文档断言的 `IDX_SCHEMA` 数值、自测清单里的文件是否存在、有没有引用已删端点。
  与 `tools/lane_probe.py` 同范式：**摊开证据、只报差异、退出码永远 0**——差异不等于错误
  （有意不写进文档的内部端点也会出现在清单里），判断留给人。
  首跑就查出四处：`/api/grep` 与 `/api/stats` 从没进契约、17 个 CLI 子命令公开文档零清单、
  架构总览的 `IDX_SCHEMA` 当前值停在 10（代码 14）、`check_i18n_js.py` 是写死绝对路径与
  某次键名的一次性脚本。
- **`tools/check_i18n_js.py`**：三语键集同步 + `<script>` 语法（`node --check`）。改
  `index.html` 后跑。
- **AI 跑文档对账**：AI agent 调 `cli.py doctor` 拿规则 code 列表，与 `docs/界面导览.md` 的
  体检章节对账——能发现"代码加了规则但文档没列"的滞后。

## 执行清单：每加一个功能时跑一遍

新增功能 / 新增字段 / 新增规则时，按顺序过：

```
□ 1. 这个功能的读者是谁？归到现有受众文档（界面导览/架构总览/AI_USAGE），不轻易开新文档
□ 2. 涉及的 SSOT 在哪？字段/枚举/code 加到 SSOT 处（通常是模块 docstring）
□ 3. 文档同步：其他文档怎么引用这个 SSOT？写引用，不重复定义
□ 4. 自检句：在该章节末尾加"如果你改了 X，必须同步改这里"
□ 5. issue 同步：开"文档同步" sub-task，列涉及的文档清单
□ 6. 机器对账（如果加了端点/CLI 子命令/字段）：`uv run python tools/doc_audit.py`
□ 7. 三语更新（如果用户可见字符串）：README 三语 + 界面文案三语 + i18n key
```

**这条教训在 260729 又被验证了两次**（#13 CONTRIBUTING 的约定摘要、#14 架构总览的不变量章节），
三个实例形态各异——一行版本号、一段英文摘要、四个完整章节——但病因完全相同：

> **给腐化开的药方如果需要人工定期同步，它自己就是下一处腐化。**
> 优先选零维护的指针（链接、自动生成、真源引用），而不是可维护的副本。
> 判据很简单：**这份内容有没有第二个地方也写了？** 有就是副本，无论它当初抄得多准。

## 防腐化的边界

最后说一个反模式。**不是所有文档滞后都该修**——有些滞后是合理的代价：

- **commit history 的 `Co-Authored-By: Claude` trailer**：开源时讨论过，改写要 rebase 已 push
  的 tag，成本高收益低，**暂不动**（`issues/closed/260712_去AI痕迹与本地维护规范.md` 的决策）
- **macOS 真机测试覆盖度**：维护者在 Windows，macOS 靠 CI + 贡献者，不可能持续保持最新真实
  测试——这是已知欠债，CLAUDE.md 显式标注
- **CLAUDE.md 的"教训"段**：列的是项目结构性会再产的 bug 类型，不是当前 bug 清单——故意
  保留旧的（如 260713 的死配置描述）作为历史对照，但要明确标"已修复于 vX.X.X"避免误导

判断标准：**滞后是否会误导下一个读者？**——是则必修；只是过时但读者不会据此做错判断的，
可以延后。

## 一句话总结

> 单人维护的项目里，文档不是写给读者看的，是**写给三周后的自己看**——那时候你已经忘了这次
> 改动的所有上下文，只能靠文档对账代码。SSOT + 自检句 + issue 同步 + AI 自检，这四件套让
> "对账"这件事不必每次重新发明。
