# CC Wire Analyzer 文档维护策略

> 读者：项目维护者（单人 + AI 辅助）和想理解文档组织的贡献者。
> 这是一份**元文档**——讲文档本身怎么维护。**各文档分别是什么、该找哪份，见
> [docs/README.md](README.md)**；本篇不重复那张索引表。

## 引子：文档腐化是指数级的

> **功能增长是线性以上的，文档腐化是指数级的**——每加一个功能，旧文档都要被重读、判断是否
> 需要改、改对地方。任何一个环节漏掉，文档就和代码分叉，下次读者（人或 AI）就被误导。

这不是假设。本项目已经数次撞上，而且有个共同点值得先说：**这些腐化没有一次是文档自检发现的**
——全是有人（或某个子代理）为了别的事去扒代码时顺手撞见的。等读者撞上，就已经晚了一步。
这就是这套策略、以及后来 `tools/doc_audit.py` 存在的理由。

---

## 适合本项目的策略

cc-wire-analyzer 是**单人维护 + AI 辅助 + 开源 + 多语言读者**的项目。最致命的失败模式是
**单人维护断裂**——维护者一旦忘了一个细节，没人补位，文档就分叉。所以策略往**让机器和 AI
能自检**那端倾斜，而不是模仿企业级 docs-as-code 方案。

### 策略一：SSOT 单一真源（最重要）

> **每个事实只在一处定义，其他地方引用。** 文档互相矛盾就是没有 SSOT 的后果。

代码里项目一直在做 SSOT（`usage_norm` 归一、`IDX_SCHEMA` 版本号），文档要补上同一套哲学：
每个枚举 / 字段名 / 规则 code 只在一处权威定义，其他文档**链接过去，不重复写定义**。

| 真源类型 | 权威位置 |
|---|---|
| HTTP 端点规格 | [`reference/API契约.md`](reference/API契约.md)（`tools/doc_audit.py` 机器对账）；AI_USAGE 与 `app.py` 回落表只放速查一行 |
| CLI 子命令 | [`reference/AI_USAGE.md`](reference/AI_USAGE.md) 的 CLI 表讲「做什么 + 有没有副作用」；`--help` 是参数权威 |
| `kind` 枚举 | `classifier.py` 的 `KIND_ORDER`（常量旁带演进注释） |
| `err_kind` 枚举 | `proxy.py` 各 `error.kind` 赋值点 |
| doctor 规则 code | `doctor.py` 的 `_r_*` 规则函数 |
| 字段名双轨 | 录制格式用 Anthropic 全名、API 出参用归一后短名——在 SSOT 处显式说清 |
| **开发约定**（不变量 / 惯犯 bug / 自测清单 / 前端规则） | [`reference/开发约定.md`](reference/开发约定.md) 唯一定义，CLAUDE.md 与 CONTRIBUTING 只留指针 |
| beta 基线 | `classifier.KNOWN_BETAS`，前端由模板注入消费 |
| 索引 schema 当前值 | `classifier.IDX_SCHEMA` 常量，**文档只讲机制不抄数字** |
| 版本号 | git tag / GitHub Releases，**任何文档都不写死** |

> **自检**：新增一类真源（新枚举 / 新规则集）时在此表登记，并确认那个位置真的含有可读的完整
> 定义——别指了个空。这张表当年就漏掉「约定型真源」，于是开发约定长出了三份副本。

### 策略二：按「腐化风险 + 触发时机」组织，不按功能

目录分层（`reference/` 会腐化要对账、`methodology/` 几乎不变、根下是元文档）见
[docs/README.md](README.md)。这里只说两条容易写歪的判据：

**受众相同也要按触发时机分开。** 架构总览与开发约定读者都是开发者，但一个是「我要读懂这个
项目」、一个是「我正要动手改」——合在一份里，动手的人得翻过几百行架构叙事才找到不变量清单。

**新增功能时不要急着开新文档。** 先想读者是谁，归到现有受众文档里。比如失败聚合加了 UI 入口，
应该更新到界面导览的对应段，而不是单开一份「失败聚合功能文档」。

### 策略二·补：还有一批文档不在这个仓库里

除公开文档外，项目另有一批本地维护、`.gitignore` 排除的文件：给 AI 的本地开发约定、
改动记录（`issues/open` + `issues/closed`）、路线图构想与 UI 候选池、以及若干研究笔记。

**两套的边界是分受众**：公开文档面向公众（去内部痕迹、不含本机路径、不含维护者具体用的
上游服务商）；本地文档面向项目内部。这条治理线从项目开源那天就确立，**它同时解释了公开
文档里为什么看不到某些决策过程**——不是没记，是记在另一边。

对本篇的实际影响：**上面几种腐化形态的逐条明细在本地 `issues/closed/` 里**，公开侧只保留
归类后的教训。想追某一条具体腐化是怎么发现、怎么修的，那是 CHANGELOG 与 issue 的职责。

### 策略三：每份文档自带「自检句」

在章节末尾写一句给未来 AI/人的提示：**「如果你改了 X，必须同步改这里。」**
比机器对账更柔但覆盖更广——机器校验得了链接和端点，校验不了语义。

例：API契约的 `/api/proxy/status` 段末尾写着「加新字段时必须同步更新 `_proxy_state()` +
本契约 + AI_USAGE 的字段表」。

### 策略四：issue 先行扩展到文档同步

「改代码先开 issue」的纪律定义在 [开发约定.md](reference/开发约定.md) 第十一节，本篇不重复。
只加文档相关的这一条：

> **任何带新功能 / 新字段的 issue，必须开「文档同步」sub-task**，close 前核对该功能涉及的
> 所有文档提及处。

### 策略五：让机器和 AI 能自检

- **结构化优先**：API / 字段 / 规则用表格（机器可解析），叙事用散文（人可读）。
- **`tools/doc_audit.py`**：对账机器可判定的事实——端点是否进了契约、CLI 子命令是否有文档、
  文档指向的文件是否存在、断言的 `IDX_SCHEMA` 数值、自测清单里的文件是否存在。
  **清单以脚本 docstring 为准，这里不抄。**
- **对账范围是路径规则**：`reference/` 下的文档进对账，新增一份放进去就自动被覆盖——
  而不是维护一张「哪些文档要对账」的名单（名单正是最容易忘记更新的东西）。
- **AI 跑语义对账**：agent 调 `cli.py doctor` 拿规则 code 列表，与界面导览的体检章节对账，
  能发现「代码加了规则但文档没列」这类机器判不了的滞后。

## 执行清单：每加一个功能时跑一遍

```
□ 1. 这个功能的读者是谁？归到现有受众文档，不轻易开新文档
□ 2. 涉及的 SSOT 在哪？字段/枚举/code 加到 SSOT 处（通常是模块 docstring）
□ 3. 其他文档写引用，不重复定义
□ 4. 章节末尾加自检句
□ 5. issue 开「文档同步」sub-task
□ 6. 机器对账：uv run python tools/doc_audit.py
□ 7. 三语更新（如果有用户可见字符串）：README 三语 + 界面文案 + i18n key
```

## 腐化的四种形态（教训，非流水账）

项目至今记录过十几次文档腐化。**逐条明细不在这里**——那是 `issues/closed/` 与 CHANGELOG 的
职责，抄到这儿就是又一份会分叉的副本。这里只留归类后的病因，因为病因会重复，明细不会。

### ① 副本必然分叉，而且是在误导读者的那一刻才被发现

同一份内容存在于两处，无论当初抄得多准。**最贵的一次实例**：`CONTRIBUTING.md` 写着
「dev server 实时读模板，无需重新构建」——这句是错的（`debug=False` 下 Jinja 会缓存模板），
而它真的骗到了人：有人照做，对着缓存的旧页面查了半小时改动为何不生效。

> 副本不是「迟早会过时」的隐患，它是**已经在误导读者**的现行事实。
> **判据**：这份内容有没有第二个地方也写了？有就是副本。

### ② 需要人工定期同步的药方，自己就是下一处腐化

为了让 README 显示版本号而手写的 `Current version: vX.Y.Z` 行，**上线后第一次发版就腐化了**
（新版已发布，三份 README 仍写着旧版号）。「每次发版记得改三个文件里的一行字」这种义务
没人守得住。现在只留 Releases 链接，由 GitHub 自动指向最新，代价是读者多点一次。

> **优先选零维护的指针**（链接、自动生成、真源引用），而不是可维护的副本。

### ③ 数字抄一份就分叉

体积、条数、行数、schema 版本号——凡是能一条命令算出来的，写进文档就是下一处腐化。
本篇的文档矩阵当年有一列「当前规模（21KB / ~390 行）」，正是因此删掉；而同一时期
架构总览还写着「2558 行单文件」（实际 3873）——**规矩立了，另一份文档没跟着清**。

所以开发约定的惯犯清单里明写「一律不写条数」，而本篇上面那句「记录过十几次」也是有意含糊的。

### ④ 「某份文档提过」不等于有对账

`/api/grep` 与 `/api/stats` 长期不在契约里（AI_USAGE 提过，契约没有），17 个 CLI 子命令
公开文档零清单——注意力都在 GUI 与 HTTP 上，CLI 悄悄长到 17 条没人察觉。这类**机器完全
可判定**的事实不该靠人扒，`tools/doc_audit.py` 就是为这一类而生。

> 判断一处腐化属于哪种形态，比记住它是第几号更有用：①②③ 决定你该怎么写，④ 决定该不该
> 让机器来管。

## 防腐化的边界

**不是所有文档滞后都该修**——有些滞后是合理的代价：

- **commit history 的 `Co-Authored-By` trailer**：改写要 rebase 已 push 的 tag，成本高收益低，
  开源时讨论过，暂不动
- **macOS 真机测试覆盖度**：维护者在 Windows，靠 CI + 贡献者，不可能持续保持最新真实测试
  ——这是已知欠债，显式标注即可
- **有意保留的历史对照**：作为「这类 bug 会再产」的例证而保留的旧描述，但必须标明它是历史

判断标准：**滞后是否会误导下一个读者？** 是则必修；只是过时、但读者不会据此做错判断的，
可以延后。

---

## 一句话总结

> 单人维护的项目里，文档不是写给读者看的，是**写给三周后的自己看**——那时候你已经忘了这次
> 改动的所有上下文，只能靠文档对账代码。SSOT + 自检句 + issue 同步 + 机器对账，这四件套让
> 「对账」不必每次重新发明。
