# CC Wire Analyzer 架构总览

> 读者：想搞懂这个软件怎么搭起来的人——不论是想贡献代码的开源者、想复盘架构的设计者，还是好奇"一个 MITM 代理桌面应用怎么从零长到 v0.4.0"的旁观者。
> 配套：[界面导览.md](界面导览.md)（人看到什么）、[API契约.md](API契约.md)（接口规格）、[AI_USAGE.md](AI_USAGE.md)（agent 入门）。本篇讲**软件怎么搭起来的**。

## 引子：wire 层才是真相源头

Claude Code 自己在 `~/.claude/projects/*.jsonl` 里记录的会话历史，是**事后加工过的视图**——
system prompt 被剥离了原始水印、SSE 分块时序被抹平、安全分类器调用根本不出现、token 成本被
四舍五入。OTLP 遥测能看到指标但看不到原始字节。**真正发生的事情，只有 wire 层（CC 与上游
之间的 HTTP 流量）知道**。

cc-wire-analyzer 的工作就是把这层抬到人能看见的地方。它是一个本地 MITM 代理桌面应用：
启动时把自己的本地端口写进 `~/.claude/settings.json` 的 `ANTHROPIC_BASE_URL`（**只动这一字段**），
CC 的所有流量绕道经过它，被透明转发、流式聚合、按天落盘；关闭时按字节恢复 settings.json。

> 这个看似简单的"绕道录一下"，做对了之后能揭示一些 CC 用户根本意识不到的真相——
> 比如安全分类器调用是**非流式**的、每会话后台跑、还花钱（实测一条 551 input + 28224 cache_read）；
> 比如 effort=max 在官方端点会让会话标题生成静默 400，CC 界面看不出任何迹象；
> 比如 5 个并行 Explore 子代理派生时全部挤在一条泳道上（260725 撞出的对齐 bug）。
> 这些都是 wire 层先看到、被项目归类成"主动诊断"方向后浮出来的。

## 血缘：三探针互补

cc-wire-analyzer 不是凭空冒出来的。它有两个前身，构成了工作区里的"三探针互补"：

| 探针 | 看哪一层 | 数据源 | 能看到 | 看不到 |
|------|---------|--------|--------|--------|
| **trace-analyzer**（前作） | CC 视角 | `~/.claude/projects/*.jsonl` | 工具调用、消息 DAG、模式与子代理、思考链（事后加工） | 原始 system 水印、SSE 时序、上游真实响应 |
| **prompt-conflict**（前作） | cc-switch 视角 | `cc-switch.log` | CC 发出的提示词全貌、CLAUDE.md 冲突 | wire 层、jsonl 层 |
| **cc-wire-analyzer**（本作） | wire 层 | CC ↔ 上游 HTTP 流量 | system prompt 原始水印、SSE 分块时序、安全分类器、精确 token、上游限流头 | CC 内部状态、cc-switch 配置 |

三者互补：wire 代理录原始 → jsonl 是 CC 的事后视角 → OTLP 是指标。**前作看不到的链路级真相，
正是本工具的存在理由**。

## 五层架构总览

整个软件可以拆成五层，从外到内、从硬到软：

```
┌─ 第零层：外壳（人/AI 怎么进入这个软件）─────────────┐
│  desktop.py 单 exe 双模式 + cli.py agent 命令行       │
│  + GitHub Actions 双平台 CI                           │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─ 第一层：录制基座（不能出错的部分）────────────────┐
│  proxy.py MITM 透传 + SSE 流式聚合                    │
│  capture_store.py JSONL 落盘 + 写时索引 + LIVE SSE    │
│  settings_guard.py BASE_URL 安全 patch/restore        │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─ 第二层：分析（从录制到洞察）─────────────────────┐
│  classifier.py 请求分类 + DAG 构建                    │
│  doctor.py 配置体检（8 条只读规则）                   │
│  diagnose.py 失败聚合（错误指纹归并）                 │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─ 第三层：交互（人 + agent 消费）───────────────────┐
│  app.py Flask 后端（~20 个 API）                      │
│  templates/index.html 前端单文件（4 视图）            │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─ 第四层：LLM 工具（增值功能）──────────────────────┐
│  翻译 / AI 解读（带防注入隔离）/ 格式化               │
└──────────────────────────────────────────────────────┘

  + 第五层：辅助系统（贯穿所有层）
    config.py 配置持久化 / *_selftest.py 测试套件 / .github/workflows/ CI
```

每层的核心契约：

- **外壳**：把人或 AI 安全地接进软件，关掉时无论用什么姿势都不会留下死代理端口
- **录制基座**：把 wire 流量**透明**地录下来——CC 体验不变、录不到也不许把 CC 弄挂
- **分析**：从录制里提取结构——一次请求是什么角色、今天失败都是些什么、配置有什么矛盾
- **交互**：把结构和原始数据**按受众**呈现——人看 GUI、AI 走 CLI/API
- **LLM 工具**：在原始数据上提供增值能力——翻译、解读、格式化

下面逐层拆解。

## 第零层：外壳——人/AI 怎么进入

整个软件对外的可执行入口只有一个：`desktop.py`（Windows 是 `cc-wire-analyzer.exe`，macOS 是
`CCWireAnalyzer.app`）。它按 `argv` 切两种模式：

| 模式 | 触发 | 干什么 | 给谁 |
|------|------|--------|------|
| **GUI** | 双击 / 无参 | pywebview 开窗（1280×840），渲染 `templates/index.html` | 人 |
| **serve** | `serve` 子命令 | headless Flask + 自动 patch 代理，不开窗 | AI agent |

### 为什么是单 exe 双模式

这是项目最反直觉的取舍之一。Windows 的 `console=False`（noconsole）打包让双击不弹黑窗，但
副作用是 `sys.stdout is None`——"AI 要 stdout"和"双击不弹窗"在单 exe 里看起来互斥。

> 但 AI 真的需要 stdout 吗？不需要。`app.py` 早就有完整 HTTP API 给前端用，AI 调它们拿结构化
> JSON 比读 stdout 还方便。260713 用户点破这件事："AI 控制只要有办法启动停止就行了吧，
> 数据都有存储和日志"。于是双 exe 合并成单 exe，体积从 51MB 砍到 27MB。

### pywebview 三大坑

桌面外壳的核心挑战是 pywebview 在跨平台/退出路径上的几个硬伤：

1. **`closing` 是唯一同步派发的关窗事件**——`closed` 是异步的（后台线程），退出竞态下不可靠。
2. **macOS Cmd+Q / 红点关窗走 `NSApp terminate` → C 层 `exit()`**，绕过 Python 的 `finally` 和
   `atexit`——只有 `closing` 能兜住（260713 用户实测踩穿，260714 Apple Silicon 真机复测确认）。
3. **`_restore_on_close` 绝不返回 False**——pywebview 把"有 handler 返 False"当取消关闭，用户
   就关不掉窗了。异常也必须吞掉（恢复失败不能演变成关不掉窗）。

这三条决定了"`closing` + `os._exit(0)` 跳 atexit + finally 手动 restore"这套退出路径，是
macOS 上保证 settings.json 不被留在死代理端口的命脉。

### 跨平台分发

CI 在 `.github/workflows/release.yml`，`v*` tag 触发双平台并行构建：

- **Windows**：PyInstaller + WebView2（系统自带）+ UPX 压缩 → 单 `.exe`
- **macOS**：PyInstaller + WebKit via pyobjc + `ditto` 打 zip → `.app` 目录
- **字体打包**：Inter / JetBrains Mono / Noto Sans SC（SIL OFL）随 `src/static/fonts/` 一起进 exe，
  保证跨平台视觉一致；同目录还有 `marked.min.js` + `purify.min.js`（vendored 前端库，离线必须）

> **维护者在 Windows，macOS 靠 CI + 贡献者验证，不本地测**——这是 v0.1.0 立下的已知欠债，
> 260714 在 Apple Silicon + pywebview 6.2.1 上真机回测填过一次，每次有大版本跳跃都要重测。

### release 编排的两条教训

v0.1.0 首发踩了两个坑（都用注释固化防再撞）：
1. **并发 attach 丢 asset**：两个 build job 各自 attach 同一 release 会并发写、互相覆盖，v0.1.0
   的 Windows exe 就这么丢了——改用单独 `release` job `needs: build` → 一次性下载所有 artifact →
   一次 attach
2. **release notes 被吞**：单人项目无 PR，`generate_release_notes` 只剩一行 "Full Changelog"
   链接——改成从 `CHANGELOG.md` 按段落提取，三层 fallback（CHANGELOG → tag message → 占位）

## 第一层：录制基座——不能出错的部分

这一层是项目的命脉。**CC 的所有流量都经过这里**，错了就把用户的 CC 弄挂。三条铁律贯穿：

1. **代理的透明性优先级最高**——录不下来也不许把 CC 弄挂
2. **settings.json 只动 BASE_URL 一字段**——绝不整文件回滚
3. **CC 绝不能被留在指向死代理端口的状态**——六重恢复 + 跨重启自愈

### 1.1 MITM 透传代理（`proxy.py`）

**职责**：Flask catch-all 路由调它，把请求透明转发到 `settings.json` 原始 BASE_URL，httpx
`stream=True` 边收边 `yield` 给 CC、累积 chunks，请求结束时聚合 SSE/非 SSE 响应落盘。

#### SSE 边转发边录（最反直觉的取舍）

```
CC ←─yield chunk─── proxy.generate() ──── iter_raw ──→ 上游
                       │
                       └─→ chunks.append(chunk)  ← 同时累积
                       └─→ chunk_times.append(...)  ← ttft 算法用
```

为什么不先录后转？一旦 buffer 完整响应再返回，**流式特性全破坏**——CC 思考链/SSE 分块时序
与直连不一致，代理的透明性就没了。代价是 generator 要兼任两条路径（转发+录制），逻辑更绕；
客户端断开也要录（`finally` 兜底）。

#### SSE 聚合（`_parse_sse`）

Anthropic Messages SSE 流按 `"\n\n"` 切 event、按行拼 `data:`、`json.loads` 后按 type 分发：

- `content_block_start` 建 block；`content_block_delta` 按 `text_delta`/`thinking_delta`/`input_json_delta` 累加
- `content_block_stop` 把 `_input_raw` `json.loads` 成 `input`，**失败保留 `input_raw_fallback` 不静默丢**
- `message_delta` 取 stop_reason + usage；`message_start` 取 input usage
- `blocks: dict[index, block]`，最终按 sorted keys 输出 list
- `ttft_ms = chunk_times[0]*1000`（首 chunk 时间近似首字节时间）

#### 非流式响应（260713 补全的关键路径）

原代码非 SSE 分支只扫 JSON 顶层找 token 键，恰好命中 `count_tokens` 的形状；普通 `/v1/messages`
非流式响应的 usage 嵌在 `j["usage"]` 下扫不到——**整笔 cost 丢失**。

> 这个 bug 能活到 260713，是因为自测只测了流式那一条路（[开发指南.md](开发指南.md) 惯犯 bug ④「测试数据不像真流量」）。
> 更关键的是：CC 的**安全分类器调用就是非流式**——每个会话后台跑、用户看不见、还花钱。
> 这恰恰是本工具最该揭示的成本，结果被自己扔了。补全后非流式分支也走 nested usage +
> stop_reason + content_blocks 提取。

#### 错误分类

| 异常/状态 | `rec.error.kind` | 转发给 CC 的状态 |
|---|---|---|
| `httpx.ConnectError` | `connect` | 502 `upstream_connect` |
| `httpx.TimeoutException` | `timeout` | 504 `upstream_timeout` |
| `httpx.HTTPError`（其他） | `http_error` | 502 `upstream_error` |
| 上游 status ≥ 400 | `upstream_4xx` / `upstream_5xx` | 原样透传 + body_snippet[:500] |

所有错误路径都 `capture_store.append(rec)`——失败也要录，这是诊断的原料。

#### 自指守卫（260718 v0.3.1 P0 修复）

`forward` 里 `upstream == get_patched_listen()` → 502 `self_reference_upstream`，宁可错杀也不
无限递归。**精确比端口**而不是粗暴拦所有 loopback——放行合法的本地 OpenAI 兼容上游（如
`:8080` vLLM）。

这是 v0.3.0 watcher 引入的新代码路径暴露的 P0 回归。完整根因链是真机日志还原的：用户某次
空窗期 settings.json 被外部改成 5051 → 新进程 `snapshot_original()` 读到 5051 没自指守卫 →
当真上游记下 → patch 写 5051（文件本就 5051，等于没改）→ marker 记 `{original:5051,
listen:5051}` → CC 请求 forward 转给自己 → 死循环 → 全 504。snapshot 自指守卫是第一道，
proxy.forward 是最后一道深度防御。

### 1.2 录制存储与索引（`capture_store.py`）

**职责**：append-only JSONL 按天落盘 + 写时索引 + 内存 deque + SSE 广播 + 启动期保留天数清理。

#### 写时索引 vs 读时算（最关键的性能取舍）

单条 record 可超 5MB（完整 system prompt + 71~100 个工具的 JSON Schema），一天录制上 GB
（实测 826MB/2993 条）。两种方案的实测对比：

| 方案 | list_captures 826MB | DAG 构建 | 详情打开 | 峰值内存 |
|------|---------------------|----------|----------|----------|
| 读时算（v0.3.1） | 2.6s | 5s（每次重读重 parse） | 数秒～数十秒 | 3.3GB |
| 写时索引（v0.3.2） | 1ms | 147ms | 22ms | 0.1MB |

写时索引的代价是：record 在 `append()` 时本就在内存，顺手 `classifier.index_record` 成 1~2KB
索引记录写进 `{date}.idx.jsonl`（含主文件字节偏移 `off`/`len`）。之后列表/DAG 只读索引，详情按
偏移直接 seek。

#### 索引 schema 版本号（防静默缺字段）

`IDX_SCHEMA = 4`（当前，v0.4.0 bump 自 3）。字段集变了必须 bump，否则旧索引"结构有效"但新字段静默缺失、判别
逻辑悄悄退化成回落分支，**没有任何东西会报错**——[开发指南.md](开发指南.md) 惯犯 bug ②「键名错位」的同型再现。

发现版本不符的处理有讲究：**必须先 `unlink` 再返回空**。否则 `_backfill_index` 是 append 模式，
旧条目留在文件里下次读又判过期 → 每次读都重复回填一整天。

#### LIVE SSE 广播

```
capture_store.append(rec) ──┬─→ 主文件 {date}.jsonl（ab 模式 tell=off）
                            ├─→ 索引 {date}.idx.jsonl（同 _LOCK 内）
                            ├─→ _LIVE_DEQUE.append(摘要)  ← maxlen=200
                            └─→ 遍历 _LIVE_SUBSCRIBERS put(q, 摘要)
                                                ▼
                            /api/captures/stream SSE 推送给前端
```

`_public_summary(idx)` 剥掉 `_IDX_PRIVATE`（off/len/v + 所有分类原料字段）→ 列表/SSE 输出形状。
落盘失败时**仍推 LIVE**（流量确实发生了，用户有权看到），但标 `not_persisted: True` 让状态栏
告警——"界面在跳、盘上没字节"的静默数据丢失是 v0.1.0 时代踩过的坑（惯犯 bug ③「静默吞异常」，见 [开发指南.md](开发指南.md)）。

#### archive 锁内只 rename、锁外压缩

压缩数十 MB 数秒，全程持 `_LOCK` 会阻塞 CC 请求。rename 是同卷原子操作（毫秒级），抢到之后
代理若继续 append 当天 → 创建新文件（=清除"到目前为止"，符合存档语义）。压缩失败把 staging
rename 回原位 + 清 dst，不丢数据。

#### enforce_retention（260713 接上的死配置）

`enforce_retention(days)` 在 `app.py` import 期跑一次，按文件名字典序比（YYYY-MM-DD 字典序 =
时间序），**不碰 mtime**（mtime 会被拷贝/同步改掉，文件名才是事实）；**绝不碰 `archives/`**
（用户显式存档的）。结果经 `/api/about` 回给设置页显示——让功能"看得见地在工作"。

### 1.3 settings 守卫（`settings_guard.py`）

**职责**：patch 用户的 `~/.claude/settings.json` 的 `env.ANTHROPIC_BASE_URL`（**只动这一字段**），
保证停止/崩溃/被外部覆盖时**万无一失恢复**，或**决不覆盖用户的新意图**。

#### patch 流程

```
/api/proxy/start
  ├─ doctor.check()                  ← 体检，error 级 409 拦下（?force=1 越过）
  ├─ snapshot_original()             ← 读 BASE_URL + 自指守卫
  ├─ backup_file()                   ← 整文件备份到 backups/（留最近 5 份）
  └─ patch_base_url(local_listen)    ← 原子改写 + 写 marker
```

#### marker 文件——跨进程真源

`.patched` 文件结构：`{original, listen, had_key, at}`。

为什么不放内存？进程被强杀后内存状态全丢。marker 文件让"进程死亡"变成持久化状态——下次启动
能扫到残留 marker 自愈。同时它也是**跨进程真源**：CLI（独立进程）问"现在代理开着吗"必须读
这里，不能看本进程的 `is_patched()`，否则会把别的进程 patch 出的 loopback BASE_URL 误报成
残留（260725 加这条守卫时坐实的）。

#### restore 守卫——"只撤销还能证明是自己做的那一笔"

restore 前必须比对当前 BASE_URL 是否仍等于 marker 记的 `listen`：

- **相等** = 还能证明是我们 patch 进去的 → 按原值写回（或 `had_key=False` 时删键）
- **不等** = 用户/cc-switch 已自行改动 → **只清状态 + marker，绝不碰 settings.json**

这条守卫防的是"陈旧 marker 拿过期信息覆盖用户新配置"，最严重的形态：`had_key=false` 的陈旧
marker 会**直接删掉**用户刚设好的 BASE_URL。

#### 六重恢复

CC 绝不能被留在指向死代理端口的状态。为此堆了六层：

1. **GUI `closing` 事件**——pywebview 唯一同步派发；macOS Cmd+Q / 红点都必经此回调
2. **GUI `finally` 块**——`os._exit(0)` 跳 atexit，关窗前手动 `_safe_restore` + 写退出日志行
3. **`atexit`**——serve 模式靠它兜底
4. **SIGTERM/SIGINT**——serve 模式 AI `kill` 进程时命中（Windows 主线程外注册会失败，warning 后 atexit 兜底）
5. **`sys.excepthook`**——未捕获异常触发
6. **orphan-marker 跨重启自愈**——强杀（TerminateProcess）/断电到不了上述任何回调 → marker
   残留 → 下次任意模式启动 → `check_orphan_backup()` → `recover_from_orphan()`

> 第六重是真正"防强杀"的兜底，但它的判定有讲究——**marker + URL 双条件都要满足**，否则当
> 陈旧/污染 marker 处理（只清不恢复）。260718 加了一条额外守卫：marker.original 若是本地
> 回环（说明上一版守卫不住、把残留 patch 值当 original 记下了）→ **只清 marker，绝不恢复**。

#### 外部变更检测（cc-switch 共存关键）

`_settings_watcher` daemon 线程每 2s 调一次 `check_external_change`。**刻意不用 mtime 基线**：
"首轮 stat 建基线"在 patch 完成 → watcher 首轮之间有 0~2s 竞态窗（e2e 实测踩中），改成直接
读 settings.json 比 `env.BASE_URL` 字符串值。

发现外部改动 → 只**降旗**（清 `_patched` 状态 + marker），**绝不回写**——新值是用户的新意图。
用户想重新接管 = 显式再走一次 `/api/proxy/start`（snapshot 自然收编新上游）。

#### 原子写保行尾风格

`_atomic_write` 先读 raw bytes 探测 `\r\n` 与末尾 `\n`，对应输出 `newline="\r\n"` 或 `"\n"`。
**只动 BASE_URL 一字段**意味着连行尾符都必须原样——否则 Windows text mode 把 LF 隐式转 CRLF，
污染整个 git diff。

## 第二层：分析——从录制到洞察

录制基座把字节录下来，分析层把字节变成结构。

### 2.1 分类与 DAG（`classifier.py`）

**职责**：从索引记录推断三种结构——请求是什么角色（`kind`）、属于哪条会话线（`lane`）、与其他
请求的关系（`edge`）。纯函数无状态，不落盘。

#### kind 分类——子代理权威位

7 种 kind：`main` / `subagent` / `title` / `compact` / `security` / `count_tokens` / `other`（每种 kind 的报文形态、CC 为什么发它、怎么从一条录制认出来，见 [报文解读.md](报文解读.md)）。

判子代理**只认** system block[0] 计费头的 `cc_is_subagent=true`——CC 自己在 wire 上标的权威位，
8/8 子代理带、7/7 非子代理不带（260725 实测）。

> 这条规则来之不易。260713 用户反馈"很多子代理被视作主线"，项目判断"手上录制不够"——
> 12 天里跨 7-12/7-14/7-17 三批录制派生数都是 0，**改规则就等于在测量之前先扰动被测对象**。
> 260725 用完全隔离的采集路径抓到 15 条真录制，发现 CC 自己在计费头标了身份，**不需要任何
> 启发式**。准确率 10/15 → 15/15。

#### 别再重复推翻过的假设

260725 同批数据**推翻了三个看起来都很合理的原假设**：

| 假设 | 看似合理因为 | 实测打脸 |
|------|-------------|----------|
| 子代理用不同的 session_id | "儿子应该有新 id" | 子代理**复用**父 session_id（13/15 同会话） |
| entrypoint 区分主子 | "子代理应该带不同标记" | `cc_entrypoint` 被子代理**继承**（15/15 都是 sdk-cli） |
| 子代理不带 Agent 工具（"禁套娃"） | "子代理不该再派生" | general-purpose 子代理**带** Agent 工具（75 个） |

加一条 prompt 对齐的伴生发现：子代理首条 user 也被注入 `<system-reminder>`，派生 prompt 被推
到 reminder 之后——对齐**必须先剥 reminder 再按子串搜**，前缀 startswith 实测命中 0/8。

[开发指南.md](开发指南.md) 把这些固化成「子代理判别定案」段，配套 `tools/lane_probe.py` 回归探针——换 CC
版本或新形态时跑它，把权威位 / session_id / entrypoint / agent 指纹 / prompt 对齐摊开与分类器
双向交叉核对。

#### lane 分组——session_id 优先

`_lane_key`：优先 CC 会话 id（`X-Claude-Code-Session-Id` 头，回落 `metadata.user_id` JSON 内
session_id），缺则回落首条 user 文本 + uid 的 md5。

260725 前用文本 hash，866MB 天分出 42 组 vs 真实 13 会话——autocompact 压缩后 messages[0]
变了就断成新 lane。改成 session_id 后这个局限消失。

> 但 session_id 只能当**lane 键**，不能判 main/subagent——子代理复用父 session_id。
> 这是"权威位判身份、session_id 分泳道"的分工。

#### build_dag 三种边

| type | 含义 | 强弱 |
|------|------|------|
| `trigger` | 主线 Task/Agent 派生 prompt 命中子代理首条 user | 强（因果）|
| `seq` | 同 lane 时序相邻 | 强（时序）|
| `near` | aux 节点 → 时序最近主线 | 弱（仅邻近示意）|

trigger 边的对齐逻辑用 `task_prompts`（主线响应里 Task/Agent 工具的 input.prompt）去子串匹配
其他请求的 `first_user_task`（剥 reminder 后的首条 user 前 600 字）。

> 这套对齐在"并行同模板派生"场景下曾撞车——5 个 Explore 子代理的派生 prompt 前 120 字相同，
> 全部命中 prompts[0]，归到同一条泳道。**v0.4.0 已修**（`PROMPT_PROBE_LEN` 120→300、
> `PROMPT_MATCH_LEN` 200→1000、实例键改 `{mid}|{p[:1000]}`、`IDX_SCHEMA` 3→4 触发旧索引重建），
> 仅剩"前 300 字仍完全相同"的边界情形留待双向匹配策略。

#### pure_chat 回填

整轮 `turn_start=True` 且 `tool_uses=0` → 标 pure_chat（"回顾一下干了什么"这类没动手的轮次）。
前端降档渲染（虚线边 + 💬）。**刻意不靠语义关键词**——"回顾这个 bug 然后修掉它"是干活，
所以"回顾/总结"不能当判据。

### 2.2 配置体检（`doctor.py`）

**职责**：开代理之前跑 8 条只读规则，回答"配置有没有矛盾"。三条铁律：

1. **绝不写入** settings.json/凭据、不提供自动修复（与 settings_guard 不变量③同源）
2. **宁可漏报不可误报**（误报比漏报更伤——第二次误报之后横幅再没人看）
3. **绝不把用户锁死**（error 级拦启动但必须留 `?force=1` 逃生门，规则可能错）

8 条规则覆盖三类问题：BASE_URL 残留（dead_port / self_reference / half_switch）、OAuth 凭据
（expired / expiring_soon / overrides）、effort 配置（level_conflict / max_rejected_upstream）。

> 其中 `effort_max_rejected_upstream` 是项目**自己撞出来的真问题**——维护者本机顶层
> `effortLevel: low` + env `CLAUDE_CODE_EFFORT_LEVEL: max`，env 优先，会话标题请求全 400
> 静默失效。CC 界面看不出任何迹象。规则就是从这次实测里提炼的——**反复出现的失败模式
> 固化成体检规则**，这是项目的既定范式。

体检有天然盲区：读 settings.json 文件，但 CC 进程跑的是它启动时注入的进程环境。`scope` +
`scope_note` 字段就是主动交代这个边界——"体检说没问题 ≠ 现在跑着的 CC 没问题"，因为文件改了
不重启 CC 看体检会误判。

### 2.3 失败聚合（`diagnose.py`）

**职责**：把当天所有失败按 `(err_kind, status, 错误消息指纹)` 归并，**只整理数据不调 LLM**，
分析交给外面的 CC/agent。

#### 指纹归并

错误消息里的 `req_[A-Za-z0-9]{6,}` → `<request-id>`；UUID → `<uuid>`；4 位以上数字 → `<n>`。
同一根因的错误消息（抹掉请求级随机量）归一组。实测 2719 失败 → 7 组 0.09s。

#### req_fields 单值/列表语义（最反直觉的设计）

每组摆出请求侧字段（model/effort/thinking/stream/max_tokens/tools_n）：

- **单值** = 全组在这字段上完全一致 → **可能是病因**
- **列表** = 跨多种值都出现 → **排除了这个字段当因**

> 这套语义的威力在例子：一组 19 条 `effort 'max' is not supported when thinking is disabled`，
> `effort: max + thinking: disabled` 都是单值（**可能病因**），`model: [glm-5.2, glm-5v-turbo]`
> 是列表（**排除模型当因**）。光看这一行就知道病根。

#### UI 还没接入（已识别的最大缺口）

项目自承："UI 还没接失败聚合，目前只有 API + CLI（给 agent）。人看的界面里还没有
'今天失败都是些什么'的入口。"——补 UI 入口是当前的最高优先项，见 [CHANGELOG.md](../CHANGELOG.md)
顶部速览的「下一步」。

## 第四层：LLM 工具——增值功能

在原始录制数据上提供三种增值能力，都走用户配置的 LLM（OpenAI 兼容）：

### 4.1 翻译（`/api/translate`）

SSE 流式，输入截 20000 字。调 `_translate_parts` + `_llm_chat_stream`。每段大文本的工具条上

带**防注入隔离**：用户内容外层包定界符，定界符头尾硬编码、用户自定义 prompt 不可覆盖；字面

AI 解读。前端用 `marked.js + DOMPurify` 渲染，DOMPurify 消毒所有上游内容——存储 XSS 不可能
（安全不变量④）。

> **复制链路是隐形工程**：WebView2 把原生右键菜单绑 debug 开关、macOS WebKit 干脆没 Edit
> 菜单，复制全靠前端自绘右键菜单兜底。新增展示组件都得配 `.excerpt` 或自绘 ctxmenu 入口——
> 这是开发者门槛，对最终用户透明。

## 数据流：一次 HTTP 请求从到达到看见

完整生命周期：

```
CC 发请求
  │
  ▼
Flask /<path:path> catch-all（app.py:595）
  │
  ▼
proxy.forward(path)
  ├─ settings_guard.get_original_base_url() 取上游
  ├─ 自指守卫：upstream == 本代理 listen ? → 502
  ├─ capture_store.new_record() 填 method/path/upstream/headers_safe/body
  ├─ httpx.send(stream=True)
  └─ return Response(stream_with_context(generate()))
       │
       │  generate() 内每个 chunk：
       │    chunks.append(chunk); chunk_times.append(...)
       │    yield chunk  ───► CC 端实时收（不缓冲）
       │
       ▼  finally 块（客户端断开也跑）
  _finalize(...)
   ├─ 拼接 chunks → _decode_body(gzip/br/deflate)
   ├─ is_sse ? _parse_sse : 抽 nested usage/content/stop_reason
   ├─ status≥400 → rec.error.kind = upstream_Nxx
   └─ capture_store.append(rec)
        │
        │  with _LOCK:
        │   a. 主文件 ab 模式 seek(0,2) tell=off
        │   b. write(bytes) 失败 → _WRITE_ERRORS++（不阻塞转发）
        │   c. classifier.index_record(rec) + {off,len,v}
        │   d. 写 {date}.idx.jsonl 失败 → _IDX_ERRORS++
        │   e. 更新 _IDX_CACHE
        │  锁外：
        │   f. _public_summary(idx)
        │   g. not_persisted? 标记
        │   h. _LIVE_DEQUE.append
        │   i. 遍历 _LIVE_SUBSCRIBERS put(q, summ)
        │
        ▼
   /api/captures/stream SSE → 前端 EventSource
   前端 rAF 节流渲染：列表顶部插入 / DAG 增量 append（800ms 防抖）
```

**时序关键点**：
1. catch-all 与 `/api/*` 后端共一个 Flask 同进程同端口
2. `proxy.forward` 直接 import 调用 settings_guard / capture_store，无 IPC
3. LIVE SSE 与代理转发完全异步（SSE 客户端阻塞读 queue，append 时广播）

### 阶段转折的本质

> v0.4.0 之前（阶段二），价值主张是"让链路级真相**被动可观测**"——数据在盘上、界面能画出，等人去看。

## 设计哲学：四条反复出现的原则

扒完全部模块和演进史，四条原则反复出现：

### (a) 零侵入——只改一字段，字节级复原

settings.json 只动 `ANTHROPIC_BASE_URL`，恢复时"改回原值"而非"整文件回滚"。代理期间用户、
CC、cc-switch 都可能动过别的字段，整文件回滚等于偷偷撤销别人做的事。**优先级高到——录制
写盘失败都不许阻塞转发**（"录不下来也不许把用户的 CC 弄挂"）。

### (b) 万无一失恢复，重于一切

CC 绝不能被留在指向死代理端口的状态。六重恢复 + orphan-marker 跨重启自愈 + closing 同步事件
+ 自指守卫三层防御——为了搞清楚 macOS Cmd+Q 走 `NSApp terminate → C 层 exit()` 绕过 Python
finally/atexit，260713 单独踩过这个坑。

### (c) 宁可漏报，不可误报

doctor 和 diagnose 都贯彻这一条。"用户看到一个不存在的'问题'，比漏掉一个真问题更伤——
第二次误报之后横幅就再也没人看了。" 这背后是对**工具可信度会被快速消耗**的认识。配套做法：
从失败聚合反向找真样本（"7-18 那天 19 条 401 而 model 是 claude-fable-5"），攒齐了再上规则。

### (d) 测试数据必须像真流量，否则它只是在验证自己的幻觉

[开发指南.md](开发指南.md) 惯犯 bug ④的直接表述。dev_seed 改造前没有计费头/session 头/reminder 包裹，于是身份和
会话逻辑一条都测不到，UI 自测一路绿灯。这条原则适用于测试数据，也适用于一切"看起来合理
但没被真数据验证过"的设计假设——260725 那批 15 条真录制推翻三个原假设，就是这种怀疑的兑现。
