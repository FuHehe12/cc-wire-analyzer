# wire 分析器同类工具构建手册

> 读者：要给**另一个 AI 编程工具**（Codex CLI、opencode、Cursor、自研 agent……）做同类流量
> 分析器的人和 AI。触发时机：**立项之前**。
> 配套：[架构总览.md](../reference/架构总览.md)（cc-wire-analyzer 具体怎么搭的）/ [开发约定.md](../reference/开发约定.md)
> （改这个项目的代码时看）。
>
> 这篇**不讲实现**，讲问题：任何 harness 的 wire 分析器都必须解决哪些事、每件事的天真做法
> 为什么会错、换一个 harness 时哪些结论还成立。

## 引子：难的不是抓包

做一个「录下 AI 编程工具和上游之间 HTTP 流量」的软件，听起来就是一个反向代理加一个列表页。
cc-wire-analyzer 从 2026-07-05 做到现在，**代理转发那部分大概占了全部工作量的 5%**。

剩下 95% 花在五类问题上，每一类都不是「抓包」这个词会让你想到的东西：

1. **先搞清楚到底要录什么**——你以为自己在录「全部流量」，实际只录到了**你认识的那一部分**。
   被测工具早就声明了它接受哪些压缩格式、启用了哪些协议扩展、它自己遇到什么会报错，而我们
   没去读。代价是一整批响应录成空白，以及更糟的——**失败的请求被录成了成功**。而且当时没录
   下来的东西，事后回填不了。
2. **接管别人的配置而不弄坏它**——你要改被测工具的配置文件把流量引过来，然后在任何一种退出
   方式下都干净地改回去。做不到的后果不是录不到，是用户的 AI 工具从此连不上任何上游，而他
   **不会把这件事联想到你**。
3. **知道每条请求是谁发的**——一天几千条请求里，哪些是主线对话、哪些是子代理、哪些是工具在
   自己转圈。所有"看起来合理"的判别信号，我们试一个被推翻一个。
4. **让人和 AI 都能读**——单条记录能超 5MB，一条就塞满一个 agent 的上下文；而人看的那张图
   有 3000 个节点时会把浏览器冻住。
5. **主动把问题说出来**——录制里躺着大量上游已经诊断过一次的失败报告，但**没有人会去看**。

这份手册按十个能力单元展开，每个单元四段：要解决什么问题 / 天真做法为什么错 / 我们的定论 /
换 harness 时哪些变哪些不变。所有"天真做法"都不是假想的反面教材，**每一条都是这个项目真的
写过一遍、撞了才改的**。

## 怎么用这份手册

立项时按单元清点，每个单元先问一句：**我的 harness 在这一点上和 Claude Code 一样吗？**

十个单元里，真正 harness 特有的是**单元 0（观测面盘点）**、**单元 3（请求归属）**和
**单元 4（语义分类）**——它们依赖目标工具的具体行为，必须重新采数据。其余七个单元的结论
几乎可以原样搬走。

建议的实施顺序（不是文档顺序）：

```
先搞清对方说了什么   单元 0 盘点                     ← 产出一份对账表，不是读完就算
先拿到数据          单元 1 接管  →  单元 2 落盘
能查                单元 5 索引
知道数据是什么       单元 4 分类  →  单元 3 归属     ← 这两个要重新采数据
兑现价值            单元 7 诊断
再谈好看好用         单元 6 可视化  →  单元 8 双模式  →  单元 9 打包
```

**别倒过来做。** 先做可视化会得到一张画着错误分类的漂亮图，而你要到很晚才发现分类是错的。

**单元 0 尤其别跳过。** 它看起来不产出任何功能，很容易被当成"先干起来再说"里那个可以省的
步骤——我们就是这么省的，代价是两次不可逆的数据丢失（详见该单元）。它花的时间以小时计，
补救的代价以"当时没录下来的东西永远回不来"计。

## 单元 0：harness 观测面盘点（动手前先做）

### 要解决什么

在写任何解析代码之前，先把「这个 harness 自己声明了什么」盘干净，形成一份对账表：
**它说它接受什么、它实际发什么、它自己能消费什么**。

这个单元不产出功能，产出的是一份清单。**它是其余所有单元的前置**——不知道 harness 声明了什么，
单元 2「一条都不能悄悄丢」就无从谈起：你根本不知道什么算「丢」。

### 天真做法为什么错

天真做法只有一种，而且非常自然：**凭对协议的印象写实现，然后等真实流量把漏洞踩出来。**

它错在哪，我们用两次真实事故来说明——**同一天暴露的两次，形状一模一样**：

| | 我们的实现 | harness 早就声明了什么 | 后果 |
|---|---|---|---|
| 1 | 只实现 gzip / deflate 解压，因为"官方 API 用 gzip" | **每一个请求头**都写着 `Accept-Encoding: gzip, deflate, br, zstd` | 某个上游按声明选了 br → 安全分类器响应的 body / usage / content_blocks **整个录空**，而界面上毫无异常 |
| 2 | SSE 解析器只处理 content_block / message 系列事件 | harness 自己的 SDK 对 `error` 事件**抛异常**——它显然认为这是错误 | HTTP 200 + 错误藏在流里 → **失败被录成成功**，且失败聚合从来没统计到它，报出的失败率长期偏低 |

两条的共同点，不是"考虑不周"，而是：

> **答案一直摆在那里，我们没去读。**

第一条的清单就印在每个请求头上；第二条的清单就在 harness 自己的源码里。两次都不需要等上游
踩出来才能发现——**从 harness 声明的东西出发，当天就能列全**。

代价还不止于当下：这两次的数据丢失都**不可逆**。当时没录下来的东西，事后回填不了（见本单元
末尾「解析必须发生在录制之后」）。

### 我们的定论

**权威来源分三类，按可信度排序。加任何解析逻辑前先过一遍。**

| 类 | 它回答什么 | 怎么取 | Claude Code 的实例 |
|---|---|---|---|
| **A · 它声明的传输契约** | 这个 harness 声明自己接受什么、启用了哪些扩展 | 扫真录制的请求头全集 | `Accept-Encoding`（必须支持的解压格式清单）、`anthropic-version`、`anthropic-beta`（18 个协议扩展，随版本漂移） |
| **B · 它实际发送的字段** | 它在用协议的哪些特性、访问哪些端点 | 扫请求体顶层键全集 + 路径集合 | 13 个顶层字段、2 个端点；`context_management` / `diagnostics` 等字段直接对应 A 类里的 beta 特性 |
| **C · 它自己的消费代码** | 它**能消费**什么形态的响应＝我们必须能录什么 | 反编译/阅读其 SDK，找响应累积器的分支表 | SSE 累积器的 `switch`：有几个 `case`，就是响应形态的完整清单 |

**C 类最有力，也最容易被跳过。** 前两类只能告诉你"目前见过什么"，C 类告诉你"**可能出现什么**"
——我们少一个 case，那种响应就在录制里凭空消失，而且你不会收到任何报错。第二次事故就是漏了
C 类。

⚠️ **C 类的取证陷阱**：反编译产物里同名的 `case` 可能属于界面渲染层而不是协议层，必须逐条看
上下文。只 grep case 名会误报——我们实测抓到的 9 个 `*_delta` 里有 3 个是 UI 渲染分支。

**盘点的产出是一份对账表**，三列：`harness 声明/使用了什么` × `我们实现了什么` × `差距与严重度`。
严重度的判据只有一条：

> **数据失真（录下来的是错的）远重于数据缺失（少录了点东西）。**
> 一条请求少录一个字段，是缺陷；一条失败的请求被录成成功，是事故——**观测工具报错误率偏低，
> 比不报更糟。**

**清单会漂移，所以盘点不是一次性的。** 实测 10 天内 `anthropic-beta` 就出现 18 种组合。
把"出现没见过的声明"本身做成信号：**新的 beta 特性 / 新的编码 / 新的字段，就是下一个盲区的入口。**

### 一条独立的结构性教训：解析必须发生在录制之后

上面两次事故的数据都不可逆，根子是同一个设计选择：**我们先解析、只存解析结果**。

> 于是**解析器的认知边界就是录制的边界**。它没认出来的东西，不是"以后再补"，是**当场永久丢失**。

- 压缩解不开 → 正文没存 → 历史响应回填不了。
- 流内 error 不认识 → SSE 原文不留存 → 事后连"那几条可疑记录到底是不是错误"都查不了。

所以：**凡是"先解析、只存解析结果"的地方，都要问一句——解析失败或不认识时，原始证据还在吗？**

至少要做到**解析失败时如实落痕，不许静默留空**（我们的 `decode_error` 字段就是这么来的）。
全量留存原始字节则要与体积治理一起权衡：wire 层单日流量可达 GB 级，无脑全存撑不住。
折中方向是只对"解析结果可疑"的记录留原始字节（如停止原因缺失、出现未知事件类型）。

### 又一条结构性教训：跨观测面对账，计量单位不可直接对齐

用 harness 的**另一个观测面**（CC 的 jsonl 消息日志、OTLP 遥测）当 ground truth 验证 wire
录制时，**两边的「一行 / 一条」不是同一个东西**。我们曾拿一份 jsonl 对账 wire，看到
「jsonl 91 行 `assistant` vs wire 29 个成功响应」，差点下「wire 漏录 70%」的结论——查清后是
CC 把**一个 API 响应拆成多行 jsonl**（thinking 一行、text 一行、每个 tool_use 一行，各自独立
uuid + timestamp），实际响应数 ≈ 91 / 3.5 ≈ 26，与 wire 的 29 吻合（差是录制增长中的时序）。

> 跨观测面对账，永远按**逻辑响应边界**对齐（一次模型调用 = 一次 HTTP 请求 = 一个完整 message），
> 不能按文件行数。「行数差不多」是最不可靠的同构判据——不同观测面恰好按不同粒度切行，
> 行数比对能给出一组自信又错误的数字。

这条在 0.6.x 把 wire 层与 jsonl 层合流时是基础认知：两层数据要对齐，先统一计量单位，再比内容。

### 换 harness：变什么、不变什么

**不变**：三类来源的**分类方式**和优先级，以及"数据失真重于数据缺失"的严重度判据。
任何 harness 都在通过某种方式声明它的契约——差别只是声明在哪里。

**变**：

- **A 类的载体**。HTTP 类 harness 看请求头；如果目标工具走 gRPC / WebSocket / 本地 IPC，
  对应的是 metadata / 握手帧 / 协议版本号。
- **C 类的可得性**，这是最大的变数。Claude Code 的 bundle 可反编译，所以 C 类拿得到。
  换成闭源二进制、或经过强混淆的目标，C 类可能**根本取不到**——那就必须承认这一点，
  转而靠 A/B 类加长期观测补，并且**明确记下"C 类缺失"是已知风险**，而不是假装盘点完整了。
- **协议扩展的表达方式**。Claude Code 用 `anthropic-beta` 头列特性，别的工具可能用版本号、
  能力协商帧，或者根本不声明——不声明的，B 类（实际发送的字段）的权重就要提高。

**立项时要先查清的一件事**：目标 harness 的**错误是怎么表达的**。这一条直接决定你会不会把
失败录成成功。Claude Code 的坑在于错误有两条完全不同的通道——HTTP 状态码，以及 **HTTP 200
之下藏在流里的错误帧**。只认状态码，就会漏掉后者，而且漏得悄无声息。
**别假设"状态码 200 就是成功"**，去 C 类里找它自己在什么情况下抛错。

## 单元 1：无侵入接管上游配置

### 要解决什么

让被测工具的请求经过你，且在**任何一种退出方式**下都能干净地还原——包括正常关窗、快捷键退出、
崩溃、强杀、断电。

### 天真做法为什么错

| 天真做法 | 后果 |
|---|---|
| 备份整个配置文件，退出时整文件回滚 | 代理运行期间用户或别的工具可能改了**其他字段**，整文件回滚等于偷偷撤销别人做的事。连行尾符都会被改（Windows text mode 把 LF 转 CRLF，污染用户的 git diff） |
| 相信进程退出钩子会跑 | macOS 的 Cmd+Q / 红点关窗走 `NSApp terminate` → C 层 `exit()`，**绕过 Python 的栈展开与 atexit**。我们的三重崩溃保护在 macOS 的**正常**退出路径上全部落空，用户的 CC 每次关窗后都连不上 |
| 恢复时只信自己的备份 | 用户发现连不上后自己改了配置，你下次启动拿过期备份覆盖它。最恶劣的形态：备份记录「原本没有这个键」，于是你**直接删掉**用户刚设好的配置。用户永远不会把「我的工具又坏了」联想到「那个我刚打开又关掉的抓包软件」 |
| 快照时不校验读到的值 | 读到的"上游"如果是你自己的地址，你就会把请求转发给自己 → 无限递归 → 全部请求超时。更糟的是这个污染会写进备份文件**跨重启传播**，自愈机制反而给它续命 |
| 只在一个入口加守卫 | 我们的本地地址守卫函数写好了却只接在两个调用点上，漏了「快照」和「孤儿恢复」这两个真正会把外部值写进内存的入口——于是它以死代码的形式存在了很久，直到真机中招 |

### 我们的定论

- **只改一个字段**。恢复是「把这个字段改回原值」（原本没有就删掉这个键），不是回滚文件。
- **只撤销你还能证明是自己做的那一笔**：恢复前比对配置文件的当前值是否仍等于你写进去的那个
  地址。不相等 → 别人已经改过了 → **一律不碰文件**，只清自己的状态。
- **凡是从外部（文件、备份记录）读来一个地址准备当成"原始上游"的入口，都必须过本地地址守卫**。
  漏一个入口就等于没有。转发时再兜一层（拒绝转发给"等于自己监听端口"的地址），作为第三道防线。
- **多重恢复**：窗口的**同步**关闭事件 + atexit + 信号 + 未捕获异常钩子 + 落盘的孤儿标记（跨
  重启自愈）+ 一条不依赖任何运行中进程的独立恢复命令。注意窗口事件要挑同步派发的那个——异步
  派发的关闭事件在退出竞态下根本来不及跑。
- **优先级**：录不下来是你的损失，转发断了是用户的损失。**录制失败绝不阻塞转发。**

### 换 harness：变什么、不变什么

**不变**：以上全部。这是"接管别人的配置"这个动作的固有风险，与被接管的是什么工具无关。

**变**：

- 配置文件的位置与字段名。
- 目标工具是否支持"环境变量优先于配置文件"。Claude Code 支持，这一条极其有用——它让你可以
  **完全不碰用户的真配置**去采集流量（见单元 3 的采集姿势）。先查这一点，能省掉大量风险。
- 是否存在第三方切换工具和你争抢同一个字段。有的话，"当前值 ≠ 我写进去的值"会是常态而不是
  异常，守卫必须一开始就在。

**立项时要先查清的一件事**：改上游地址会不会让目标工具**丢失登录身份**。这在 Claude Code 上
曾是我们的默认假设，实测和官方文档都推翻了它——抢断订阅身份的只有 API key 类变量，改 base URL
不在其中，OAuth bearer 会照常随请求流入你的代理。**这个假设错了会让你走上一整条错误的技术路线**
（我们当时列了 A–E 五个候选方向，全部建立在这个错误前提上，全部作废）。

## 单元 2：全量落盘，一条都不能悄悄丢

### 要解决什么

把请求和响应完整落盘。流式和非流式都要，而且**落盘失败不能伤到被测对象、也不能悄无声息**。

### 天真做法为什么错

| 天真做法 | 后果 |
|---|---|
| 只解析流式分支（因为主流程是流式的） | 非流式响应的 usage / 内容块 / 结束原因**全丢**。而非流式恰恰是安全审查这类"用户完全看不见、却实实在在花钱"的调用——**这正是这类工具最该揭示的东西，结果被自己扔了** |
| token 用量只在 JSON 顶层找 | 两种形状：token 估算接口的响应是顶层扁平的，普通消息接口嵌在一个子对象里。只写一种，另一种静默返回空 |
| `except OSError: pass` | 写盘失败被完全吞掉，而内存队列和实时推送在 try 块之外照常执行 → **界面上列表还在实时跳，磁盘上一个字节都没有**。用户开着它跑一整天，事后发现文件是空的，而他**全程没有任何理由怀疑** |
| 把响应体截断到 N 字符当作唯一记录 | 稍大的响应就是个残缺 JSON，连事后补救都做不到 |
| 给"是否脱敏敏感头"做一个开关 | 这个开关一旦为真就是"把 API key 明文写进录制文件"的选项。而这些文件是要给 AI agent 读的——等于给密钥开了一条直通 agent 上下文的路 |

### 我们的定论

- 流式与非流式**对称解析**，两条分支各自有自测覆盖。「这个 bug 能活这么久，正是因为自测只测了
  流式那一条路」。
- 落盘失败：**计数 + 日志 + 暴露到状态接口 + 界面红色告警**，但**不阻塞转发、不中断流量**。
  「不阻塞转发」和「不告诉任何人」是两件事，别混为一谈。
- 敏感头脱敏**恒开、不给开关**。
- 归一化逻辑（比如上游字段名 → 你的内部字段名）**必须收口到一个函数**。这个错我们犯了两次，
  两次都是因为归一化被抄了好几份。

### 换 harness：变什么、不变什么

**不变**：几乎全部。"两种响应形态要对称处理"、"静默失败最伤"、"脱敏不给开关"是通用的。

**变**：响应协议的具体形状（流式事件名、用量字段名、内容块结构）。先抓十几条真流量把两种形态
都摸清楚，再写解析——别照着 API 文档写，文档不会告诉你 harness 实际发的是什么。

## 单元 3：请求归属——这条是谁发的

> **十个单元里 harness 特异性最强的一个。这一节的具体结论换个工具就不成立，但方法论成立。**

### 要解决什么

一天几千条请求，要能回答：这条属于哪个会话？是主线还是子代理？是哪一次派生出来的哪个子代理
实例？回答不了，时序图就是一团乱麻，成本也归不了因。

### 天真做法为什么错

我们试过的每一个"看起来合理"的信号，都被真实数据推翻了。**全部**：

| 候选信号 | 为什么不成立 |
|---|---|
| system 措辞指纹（"You are XXX Code…"） | 同一工具不同入口措辞不同（交互模式 vs SDK 模式），而且 SDK 模式下主线和标题生成**共用同一句** |
| 有没有派生工具（"能派生的一定是主线"） | 通用型子代理**带**派生工具 |
| 会话 id | 子代理**复用父的**。它只能当分组键，不能当身份 |
| 入口标识（cli / sdk-cli） | 被子代理继承 |
| 工具数量 | 工具**延迟注册**，同一条主线从 40 涨到 77，与子代理的区间完全重叠 |
| 用首条消息的文本 hash 当会话键 | 上下文压缩后首条消息会变 → 同一个会话断成两条泳道 |
| 派生 prompt 与子代理首条消息**前缀**对齐 | 子代理首条消息被注入了 `<system-reminder>` 前缀，派生 prompt 被推到它之后 → **前缀对齐命中 0/8** |
| 派生实例分组用派生 prompt 的前 120 字 | 「并行派生 + 同类型 agent + 模板化 prompt」三个条件同时满足时，N 个子代理的前 120 字一字不差 → 全部撞成一条泳道 |
| 派生实例分组用 `md5(派生者\|prompt)` 对齐键 | harness 后来在请求头里直接给了实例 ID（`X-Claude-Code-Agent-Id`）——精确、稳定、还能 join 被测工具的本地日志文件名 |
| 辅助调用挂「全局时序最近的主线」 | 辅助请求**也带会话头**（实测 1163 条 100% 带、99.7% 精确对上）——多会话并发日按时序挂错 9/745，按会话头挂是精确解 |

还有两个更隐蔽的：

- **分类顺序错**：我们的主线指纹判定条件极宽松，一旦先命中，后面那个更强的信号（派生 prompt
  精确对齐）连看都不会看它一眼——代码里明晃晃写着 `if kind == "main": continue`。**误判成主线
  = 终身主线。**
- **fallback 方向错**：「不认识的带工具请求 → 判成子代理」。于是任何新形态的主线都被批量降级。
  实测旧规则准确率 10/15，**错的 5 条全是主线**。

### 我们的定论

- **先找权威位**。Claude Code 在计费头里自己标了 `cc_is_subagent=true`（实测 8/8 子代理带、
  7/7 非子代理不带）。**wire 层最不该做的事，就是放着上游明明白白给的字段不用，去猜。** 同理，
  会话分组用上游给的 session id，不要 hash 用户输入的文本。
- **权威位思维要覆盖所有「归属/关联」推断，不只是身份判别**。后来我们又中过两次一模一样的招：
  子代理实例分组用 prompt 对齐推 md5 键，而 harness 在请求头里给了实例 ID；辅助调用按时序邻近
  挂主线，而辅助请求一直带着会话头。共同配方：**枚举真实录制的字段全集，凡「启发式推断 +
  官方字段已存在」的地方一律改成官方字段优先、启发式兜底**。官方 ID 还有个白捡的好处——它往往
  与被测工具本地日志（如 CC 的 `subagents/agent-<id>.jsonl`）同一 ID 空间，直接跨源 join。
- **官方字段的存在性要拿被测工具的本地日志交叉验证**。录制的头值与日志文件名/记录字段对上了，
  才算坐实「同一 ID 空间」，否则它可能只是 wire 层的临时标识。
- **两层规则**：权威位命中即判定；不命中时由派生 prompt 对齐兜底。这样即使某个版本的 harness
  不带那个标记，也不会退化成灾难。
- **对齐要剥前缀**：先剥掉注入的 reminder 块，再用**子串包含**而不是前缀匹配。
- **fallback 往保守那边倒**：不认识的带工具对话请求，默认是主线。
- **规则必须由真实流量 + 人工 ground truth 定**。我们为此卡了 12 天——手上的录制里"派生次数
  = 0"，没有子代理样本，规则就是定不了。期间做的唯一正确的事是**先不改分类器**：在测量之前
  扰动被测对象，改完也无从验证。
- **配一个探针工具**：把每条记录的全部候选信号摊开成表，与分类器当前的判断双向交叉核对。换
  harness 版本或出现新形态时跑它。这比读代码猜快一个数量级。
- **加判别原料就要给索引升版本**，否则老录制的新字段恒缺失、判别逻辑静默退化成回落分支，中间
  没有任何东西会报错（见单元 5）。

### 换 harness：变什么、不变什么

**变（几乎全部具体结论）**：

- 权威位在哪、叫什么、存不存在。别的 harness 可能压根没有——那你就只有对齐这一层，要把它做扎实。
- 子代理机制本身是否存在、是否共享会话 id、注入什么前缀。
- 上下文压缩、标题生成这些辅助调用的形态。

**不变（方法论）**：

- 先摊开所有候选信号 → 拿人工 ground truth → 逐个证伪，别从"看起来合理"出发。
- 结构信号优先于语义猜测（下一单元还会再说一次）。
- fallback 方向往保守那边倒。
- 采数据要覆盖**两组**场景，缺一不可：**串行派生不同类型**（验身份判别）和**并行派生同类型 +
  模板化 prompt**（验实例分组）。我们的测试集只有第一组，于是第二组的撞车 bug 是用户实测撞出来
  的——「只覆盖一条分支」在这个项目里反复出现，这是其中最贵的一次。

**采集姿势（强烈建议照抄）**：用环境变量让**被测工具**走你的代理，你的工具读写全是副本。被测
工具用真配置（真提示词、真模型、真凭据），只有上游地址被进程环境变量盖掉。这样采一次数据的
风险是零，不用拿用户正在用的工具当小白鼠。我们前几次采集都在真配置上做，每次都要提心吊胆。

## 单元 4：语义分类——这条请求在干什么

### 要解决什么

给每条请求一个语义角色。这不是 UI 装饰——它决定泳道归属、成本归因、诊断分组。

**这个单元的价值主张**：agent harness 发出去的请求，**大部分不是"对话"**。用户以为自己问了
一句话，wire 上是主线对话 + 标题生成 + 安全审查 + token 估算 + 上下文压缩，好几种。这些是
harness 替用户做的、用户完全看不见的事，而**看见它们正是这类工具存在的理由**。

### 天真做法为什么错

- **按 URL 路径分**：全都是同一个 messages 接口，分不出来。
- **判别顺序随意**：主线的判定条件通常最宽松，放前面会把专用类型全吃掉。**判别顺序本身就是
  规则的一部分**，要写进 docstring 并有自测锁住。
- **用语义关键词猜**：比如想识别"这轮用户只是在闲聊/让 AI 复盘"。我们认真考虑过，然后否决了
  ——关键词脆弱且**必然误伤**（"回顾这个 bug 的历史然后修掉它"是干活）。改用结构判据：**整轮
  零工具调用**。天然命中，不需要理解语义。
- **假设上游的结构化输出总是完整的**：安全审查的响应因为命中停止序列，**闭合标签常常被吃掉**，
  wire 上就是裸的 `<severity>8`。要求成对标签的解析会在真实流量上 100% 失败。

### 我们的定论

- 判别顺序固定、写进文档、自测锁住。
- **结构信号优先于语义猜测**——这是这个项目最反复被验证的一条原则。
- 每个类型都要配一句"harness 为什么会发它"，否则用户看到标签也读不懂。我们专门写了一份
  [报文解读.md](报文解读.md) 干这件事。
- 解析上游的结构化输出要**宽松匹配**，并且要如实呈现解析失败（比如"未产出判定"+ 结束原因），
  而不是渲染成空白。**一个诊断工具在自己看不懂的时候必须说出来。**

### 换 harness：变什么、不变什么

**变**：类型集合完全不同。Codex、opencode 各有各的辅助调用。

**不变**：「harness 替你发了很多你没看见的请求」这个事实，以及"判别顺序即规则"、"结构优于语义"、
"解析失败要可见"这三条。第一件事仍然是抓一天真流量，把所有不同形态的请求聚类数一数——你大概率
会发现比预想的多。

## 单元 5：大流量下的索引与查询

### 要解决什么

一天 826MB / 近 3000 条，单条可超 5MB（完整 system prompt + 上百个工具的 JSON Schema）。而
界面要能秒开列表、秒开时序图、秒开单条详情，还要实时增量更新。

### 天真做法为什么错

| 天真做法 | 实测后果 |
|---|---|
| 列表接口 `readlines()` 整个文件再取最后 N 行 | **峰值内存 3.3GB**、读盘 2.6 秒。而且倒序取的最后几行恰恰是全文件最大的那几行 |
| 时序图接口每次全量读 + parse | 单次约 9 秒；而前端每来一条新流量就防抖重调 → **流量越多调得越勤、单次还越慢**，恶性循环 |
| 详情接口逐行 parse 找 id | 最坏情况 parse 整个 826MB 才找到一条 |
| 给查询写死一个 `limit=1000` | 当天 2993 条只有前 1000 条进图，**后 2/3 的泳道根本不存在**，而界面完全不提示它截断了。用户报告的"泳道图显示不完整"就是这个 |
| 前端全量重建 DOM | 3000 节点产出 1.7MB innerHTML，单次约 1.1 秒主线程重活，实时更新时界面接近冻结 |

### 我们的定论

- **写时轻量索引**：落盘时记录本来就在内存，顺手抽出查询要用的全部字段（每行 1–2KB）+ **主文件
  的字节偏移与长度**，写一个并列的索引文件。之后列表和时序图只读索引，详情按偏移直接 seek 一行。
  实测：列表内存 3.3GB → 0.1MB、耗时 2.6s → 1ms；详情最坏情况 22ms。
- **索引带 schema 版本号**。字段集变化必须 bump，版本不符**整个索引作废重建**。不这么做的话，
  旧索引会被当成有效的，新字段恒缺失，判别逻辑静默退化成回落分支，**中间没有任何东西会报错**。
  这是我们第二次犯"键名错位"这个错之后立的规矩。
- **索引要能自愈**：缺失、落后、写了一半崩溃 → 按末尾偏移增量回填，坏行跳过且推进偏移（不要
  反复回填同一行）。
- **索引写失败绝不阻塞转发**（与主写盘同一条原则）。
- **任何"上限"要么去掉，要么显式标注 `truncated`**。静默截断是这类工具最要不得的行为。
- 前端布局若按时间递增，实时更新就只 append 新节点，泳道数变化才回退全量重渲（实测 no-op 2ms
  vs 全量 1.1s）。

### 换 harness：变什么、不变什么

**不变**：几乎全部。这是"append-only 大文件 + 交互式查询"的通用解法。

**变**：索引里抽哪些字段——取决于单元 3 和 4 需要什么判别原料。**这两个单元的结论没定下来之前
不要冻结索引 schema**，否则你会在早期反复 bump 版本、反复全量重建。

## 单元 6：时序可视化

### 要解决什么

把一天的请求流画成人能读的图：谁在什么时候发了什么、哪些是同一个会话、谁派生了谁。

### 天真做法为什么错

- **每条请求画一个等权节点**。一次用户提问会产生 N 条请求（每次工具结果回传都是一次新请求），
  于是主线上全是"中间步"，用户的观感是"分类错了，辅助请求被划进主线了"。**实际不是分类错，是
  视图粒度问题**——我们为此先全量重扫了三天录制，确认分类一条没错，才敢动视图。**用户报告的
  现象和真正的原因经常不在一个层面上，先证伪再动手。**
- **靠语义关键词区分"这轮重不重要"**：脆弱且必误伤（见单元 4）。
- **把中间步挪到辅助泳道**：会打断因果链，反而更难读。要降的是**视觉权重**，不是归属。
- **以为渲染慢是唯一问题**：3000 个等权节点即使瞬间渲染完也没法看。**过滤开关比更快的渲染更能
  解决可读性**——加了"隐藏工具循环步 / 隐藏辅助"两个开关之后，图立刻可读。

### 我们的定论

用**纯结构判据**分档，不猜语义：

| 档 | 判据 | 呈现 |
|---|---|---|
| 轮次起点 | 最后一条用户消息含真实文本块 | 大卡片（画面骨架） |
| 工具循环中间步 | 最后一条用户消息全是工具结果块 | 细条、降饱和 |
| 纯对话轮 | 整轮零工具调用 | 轻量档 + 图标 |
| 错误 | — | **永不降档**，必须刺眼 |

实测这套判据在三天真录制上和人的直觉完全吻合（某天 158 节点 = 93 细条 + 22 纯对话轮，页面高度
压缩 27%）。

### 换 harness：变什么、不变什么

**不变**：分档判据。它依赖的只是"工具结果回传也是一次请求"这个所有 agent harness 共有的形态。
"错误永不降档"、"过滤优先于渲染优化"同样通用。

**变**：消息结构的具体字段名。

## 单元 7：从录制里主动找问题

> **这是最值得优先做的差异化能力，也是最容易被排到最后的一个。**

### 要解决什么

录制里躺着大量**上游已经诊断过一次的问题报告**——上游明确告诉了你哪个字段不对、该改成什么。
但没有人会去看。

这一单元的起点是一次纯属偶然的发现：修别的东西时截图，瞥见时序图上有两张红卡，一查是上游 400
——用户机器上**会话标题生成一直在静默失败**，因为顶层配置和环境变量里的努力档位互相矛盾、环境
变量优先，而上游拒绝那个组合。工具界面上没有任何迹象。

**那两张红卡在那儿好几天了。** 这件事真正的教训不是那个 bug，而是：

> **可观测 ≠ 会被看见。** 数据在盘上、界面能画出来、等人去看——用户不会去看。真正兑现"让链路
> 级真相可观测"这个价值主张，需要工具**主动**把"录到的失败"翻译成"你的配置有什么问题"。

### 天真做法为什么错

- **把失败原样吐给 agent**：一天可能有几千条失败（我们实测过 2719 条和 2029 条），一条就能塞满
  上下文。
- **按状态码归并**：400 有很多种，混在一起没有诊断价值。要按**错误消息指纹**归并，并把 request-id、
  UUID、大数字归一化掉，否则同一个根因会碎成上千组。
- **只给错误消息，不给请求侧字段**：错误说"某字段的取值不支持"，你得同时把**这个请求的该字段
  取值**摆出来，agent 才能一步对上配置。
- **自动修复用户配置**：与单元 1 的"只撤销自己那一笔"同源。诊断只报告 + 给建议。
- **静态体检说"配置没问题"就以为万事大吉**：目标工具跑的是它**启动时**注入的进程环境，配置文件
  后来怎么改都不影响已经起来的进程。而"刚照建议改完"恰恰是用户最可能来看体检结论的时刻。

### 我们的定论

- 按 `(错误类型, 状态码, 消息指纹)` 归并。实测 2719 条失败归并成 7 组，0.09 秒。
- 每组给出**请求侧关键字段**，并且区分**单值**（组内一致）和**列表**（跨值）——**这个区分本身
  就是诊断结论**。
- **输出必须有界**：默认给前 N 组、标注 `truncated`，但组数报真实值。
- **静态体检（配置应该怎样）+ 录制诊断（实际发生了什么）互补**。后者天然免疫前者的盲区——它看
  的是实际发生过的请求。
- **体检的四条铁律**：只读、绝不自动修复；宁可漏报不可误报（规则分不清就闭嘴——误报第二次之后
  横幅就再也没人看了）；error 级可以拦但**必须留逃生门**（规则可能错，用户比规则更懂自己的
  环境）；**结论要交代自己的边界**（"这反映的是配置文件的状态，不是正在跑的会话的状态"）。
- **闭环**：真实失败 → 归纳模式 → 固化成静态规则 → 下一个用户不会再踩。上面那个努力档位的
  bug 就是这么变成两条体检规则的。**这个闭环是这一单元最有价值的部分。**

### 换 harness：变什么、不变什么

**不变**：全部方法论。归并策略、有界输出、单值/列表语义、体检四铁律、"实际 vs 应该"互补、闭环。

**变**：错误响应的具体形状、配置项集合、体检规则内容。

### 跨天视角：看复发，不只是看今天

单天诊断回答「今天出了什么问题」，跨天视角回答「这是新发还是老毛病复发、集中打在哪里」——而
**反复出现的失败模式，正是该固化成静态规则的最强信号**（上面「闭环」那一条的原料）。

跨天归并没有新发明：**用和单天同一个键** `(错误类型, 状态码, 消息指纹)` 跨天合并，不重新指纹。
新增的只是三个角度：

- **趋势**：活跃天的前半段 vs 后半段总量比——`recurring`（稳态）/ `rising`（恶化中）/ `declining`
  （自愈中）/ `sporadic`（单天偶发）。「今天又出现了，但比起上周在衰减」和「今天首次出现」是
  完全不同的处置。
- **维度切片**：失败按 host（路由供应商）/ model / harness 版本交叉。host 是 wire 层直接事实，
  **不是 model→vendor 推断**——同一个 model 可能经多供应商/中转，host 才定得了供应商（中转背后
  真正的算力供应商 wire 层看不到，但 host × model 交叉已够判断「这次失败经谁」）。
- **每日曲线**：records / failures / 去重组数 × N 天，看整体失败率走势。

**为什么不进 GUI**：跨天维度爆炸（harness 版本 × 供应商 × 时间 × 错误类型），人看是灾难。但这
恰恰是 AI 批量交叉分析的甜区——所以只走 HTTP，给 agent 审计。这是个普适判断：**维度多到人看
不过来的观测，优先做成结构化接口给 AI，而不是硬塞进界面**。

换 harness 不变：跨天用同一归并键、趋势判据、维度切片这套方法任何 harness 都成立。变的是切片
维度有哪些（Claude Code 有 host/user-agent，别的 harness 不一定；但「wire 层能直接观测的供应商标识」
这个位一定有，只是载体不同）。

## 单元 8：同一份数据，人看图、AI 读接口

### 要解决什么

这类工具的数据（完整 system prompt、分块时序、精确成本）恰恰是**AI 最擅长批量比对、人最容易
看漏**的那一类。所以它不能只有 GUI。

### 天真做法为什么错

- **给 AI 一个文件路径了事**：单条记录 5MB，agent 直接读会当场炸掉上下文。必须给"带截断的查询
  命令"，而不是路径。
- **出两个可执行文件（GUI + CLI）**：多一份要同步维护的、面向 agent 的接口，而 GUI 后端已经
  有一套了。（注意别用错理由：常见的说法是「GUI 进程是 noconsole 的，没有 stdout」——**不准确**，
  见下。）
- **以为 AI 需要 stdout**：其实不需要。GUI 的后端本来就有一整套 HTTP 接口，agent 直接调它拿
  结构化 JSON，比读原始文件还方便。
- **把文档留在仓库里，产物只是个孤零零的二进制**：使用者从 Release 下载的是单个文件，他那台
  机器上的 AI 看不到你的 `docs/`。**说明书必须随产物走**，并且要能被"第一次见到这个二进制"的
  AI 用最自然的动作找到——`--help`，以及服务起来后的一个自描述端点。

### 我们的定论

- **单个可执行文件 + 一个 `serve` 子命令**：无参数双击开窗口给人用；`serve` 起 headless 服务给
  agent 用，agent 走 HTTP。体积还小了一半（省一个重复打包的运行时）。
- **说明书打进产物，并给两个入口**：`--help` 直接打印；服务起来后 `GET /api/ai-guide` 返回同一份
  正文 + **本机运行期事实**（实际端口、数据目录绝对路径、代理是否在录）。文档里写的是
  `~/.tool/` 这种相对表述，而 AI 需要的是这台机器上的绝对路径——运行期事实那一段就是补这个差。
- **不要把"我以为的平台限制"当结论写进文档**。本项目为此空了三周：文档断言 noconsole 二进制
  "什么都打印不出来"，于是 `--help` 一直没做，别人机器上的 AI 试 `--help` 只会看到弹出一个 GUI
  窗口。实测结论是 noconsole **不分配控制台**，双击时确实没有 stdout，但被 shell 以管道/重定向
  启动时 fd 1 有效（`os.write(1, …)` 能写）——而 agent 调命令恰恰全是后一种。**平台限制类的
  断言要么给出实测矩阵，要么别写成结论。**
- **给 agent 的输出必须默认截断并标注 `truncated`**（这是一条安全不变量，不是优化）。
- **命令形状强制"先窄后宽"**：列表/搜索只回摘要和片段 → agent 先定位 → 再取单条的某一部分。
  检索姿势由接口形状强制，不靠文档提醒。
- **AI 文档的验收标准要写成一个任务**：让一个只读了这份文档的 agent 会话独立完成"找出今天耗时
  最长的那次主线请求，并说出它的 system prompt 开头"。能做到才算文档写对了。**验收要从"这台
  机器上只有那个二进制"起步**——不许预设 agent 手上有仓库。

### 换 harness：变什么、不变什么

**不变**：全部。

## 单元 9：桌面打包与跨平台

### 要解决什么

做成一个双击就能用的东西，且在两个平台上行为一致。（如果你只做 CLI 工具，本单元大部分不适用。）

### 天真做法为什么错

| 天真做法 | 后果 |
|---|---|
| 相信 GUI 主循环会正常返回 | macOS 上不会（见单元 1）。恢复逻辑写在它后面等于没写 |
| 用"已关闭"事件做清理 | 那个事件是**异步**派发的（后台线程），退出竞态下不可靠。只有"正在关闭"事件是同步派发的 |
| 以为桌面框架给了完整的浏览器行为 | WebView2 把**原生右键菜单绑在 debug 开关上**，发行版关着 debug → 右键无反应 → 用户体感"这软件的字不能复制"。macOS 的 WebKit 后端更彻底：不建原生编辑菜单，**复制快捷键完全没有响应** |
| 用 `debug=True` 一把梭解决上面那条 | 同时打开了开发者工具和一堆浏览器快捷键，发行版给终端用户不合适 |
| CI 里每个平台各自往 release 上传产物 | 并发写同一个 release 会**丢 asset**。要用单独的发布 job：等所有构建完成 → 下载全部产物 → 一次性上传 |
| CI 配置只在手动触发下试跑过 | tag 触发路径零覆盖。我们首次 tag 发版时 checkout 直接 fatal——tag 触发时 checkout 本身会把 commit SHA 写进 tag 引用，与"拉取真正的 annotated tag 对象"冲突。**这是"只覆盖一条分支"的 CI 版** |

### 我们的定论

- 恢复挂在**同步派发**的关闭事件上，并核实过框架源码（换大版本后要重新核实一次；我们从 5.x 跳到
  6.2.1 时重新核对过，结论未变）。
- 复制链路**全部前端自绘**：可选文本 + 复制按钮 + 自绘右键菜单 + 快捷键兜底。不依赖任何原生菜单，
  两个平台行为一致。代价是**新增展示组件都要记得配上入口**，这是持续的开发者门槛。
- 维护者只在一个平台上开发是常态，**另一个平台的验证要写进流程**（CI + 该平台的贡献者），并把
  这条欠债显式写进文档，别假装覆盖了。

### 换 harness：变什么、不变什么

与 harness 无关，与你的 GUI 技术栈有关。但"退出路径要覆盖全"、"CI 的每条触发路径都要真跑过一次"
是通用的。

## 单元 10：盲区雷达——协议演进预警 + 迁移时的协议发现

> **这一单元回答的是「协议变了 / 换框架了，我怎么知道」。它是这套工具里最适合原样搬走的差异化能力。**

### 要解决什么

agent harness 的协议一直在变：CC 启用新 beta 特性（web_search、advanced-tool-use……）、引入新
请求字段、发明新响应块类型。这些变化**静默发生**——没人通知你，录制里多了你认不出的字段，而你
可能根本不知道。

两个场景都卡在这：

1. **已知框架演进**：CC 升级后流量里冒出 `tool_use.caller`、`thinking.type=adaptive`——你的分类 /
   渲染逻辑没处理它们，但不会报错，只是悄悄退化（走 default / 漏字段）。等你发现时，可能已经
   录了几周的不完整数据。
2. **迁移到新框架**：从 CC 迁到 codex / opencode，新框架的请求形状完全不同。它的字段集是什么？
   不靠人猜——靠扫真实流量。

### 天真做法为什么错

- **靠人翻 jsonl**：GB 级录制，人眼找「没见过的字段」既慢又不全。我们首跑就发现了 6 类盲区，
  全是 CC 启用了一阵子、但我们完全没解析的字段。
- **靠「我知道协议」的印象**：协议在变，印象会过时。`thinking.type` 你以为是 enabled/disabled，
  实际 opus-5 出了 adaptive。
- **一次性穷举字段**：今天写全了，明天 CC 发新版又冒新的。字段集是移动靶。

### 我们的定论

**把「未知」本身做成可查询的东西**，而不是假装穷举了已知。

机制（`/api/unknowns`）：
- 录制时对每条请求算 `unknowns`——凡是命中**已知集合**（`KNOWN_BLOCK_TYPES` / `KNOWN_BLOCK_KEYS` /
  `KNOWN_BODY_FIELDS` / `KNOWN_STOP_REASONS` / `KNOWN_THINKING_TYPES` / `KNOWN_BETAS`）外的值，
  就标记下来。
- 聚合端点一次返回当天所有未知值，每项带：`snippet`（值片段，不必二次调详情就能判断）、
  `hosts` / `cc_versions`（**归属**）、`betas`（特异关联的能力）、`samples`（样本 id）。

**已知集合硬编码 + 版本号**（`KNOWN_*` 常量 + `IDX_SCHEMA`）：
- 「已知」必须是确定的、可审计的，不能动态算频次（那样「已知」会漂移）。
- 稳定的未知定期并入 `KNOWN_*` + bump schema 触发重建。这是有意的循环：雷达发现 → 人确认是
  标准字段 → 并入已知 → 雷达清空这项 → 只剩真未知。我们的首跑 6 类盲区，审查后 5 类是
  Anthropic 标准字段（CC 刚启用），并入已知后 `with_unknowns` 从 259 降到 1。

### 三个反直觉的坑（260802 复查实测，做同类工具的人直接照抄结论）

**坑一：「未知」里混着三种完全不同的东西，混在一起会把人引向错误的改进。**

| 类别 | 例子 | 该做什么 |
|---|---|---|
| harness 协议演进 | CC 启用新 beta 带来 `tool_use.caller` | 加解析/渲染，并入 `KNOWN_*` |
| **上游供应商的形状差异** | 某第三方网关在响应里回 OpenAI 风格的 `tool_result` 块 | 记进兼容性清单，**别并入 `KNOWN_*`** |
| **本工具自己的降级** | SSE 在 `content_block_stop` 前断了，工具入参没拼完 | 查代理侧，与协议无关 |

第二类最阴——它长得和第一类一模一样，而并入已知集合的代价是**用第三方的形状放宽了官方链路的
判据，将来官方真出现同名异构块，雷达反而哑掉**。判别方法很便宜：**每个未知带上 host 归属**，
单一第三方 host 独占就是它。第三类要在数据结构上就分开（我们单列 `degraded` 维度）——否则真信号
会被自己的噪声顶掉（实测有一整天的"未知"全是自己的降级标记）。

**坑二：「低频 = 新出现」是错的，得跟基线比。**

我们最初让 beta 全量按频次升序上报，理由是"长尾低频特性即新能力信号"。实测：每天顶在最前的
永远是同样几个**结构性**低频的已知特性（`structured-outputs` 只在标题请求带、`token-counting`
只在 token 估算探针带）——它们低频是因为用途窄，不是因为新。正确做法是**与基线清单比**：
不在 `KNOWN_BETAS` 里的才是新的。

**坑三：想说「这个未知字段是哪个能力带来的」，裸计数做不到。**

把「该未知出现过的请求里带了哪些 beta」按计数排序，得到的永远是**每条请求都带的那几个**
（实测报出来的 5 个恰好是当日出现率 100%/96% 的前 5 个）；而只出现一次的未知，所有 beta 计数
全平局，排序退化成"取 header 里的前几个"。要回答"来源"必须算**提升度**：
`P(beta|带该未知的请求) ÷ P(beta|全体请求)`，只留显著高于 1 的。没有显著项就诚实地给空——
**空是正确答案，凑数才是错的**。

### 换 harness：变什么、不变什么

**不变**：整套机制——`_unknowns` 计算 + 聚合端点 + snippet / beta 关联 + KNOWN 维护循环。它依赖的
只是「请求有结构化字段、响应有类型化块」，所有 agent harness 共有。

**变**：`KNOWN_*` 集合本身。它是**当前 harness 的协议快照**——CC 的 KNOWN 不能照搬到 codex
（codex 的 system 措辞、字段、beta 都不同）。迁移时雷达的用法恰恰相反：

> 先跑一次新框架的录制 → 雷达报「全未知」（因为 KNOWN 还是旧框架的）→ 逐个确认每个未知是不是
> 新框架的标准字段 → 建新框架的 `KNOWN_*` → 雷达清空。

**雷达不是「已知的清单」，是「发现未知的工具」。** 迁移时它的价值最大——把「猜新框架协议」变成
「扫一遍确认一遍」。这也是为什么 snippet（值片段）+ hosts（归属）重要：迁移者看到未知，不必先调
详情就能初步判断「这是什么」，靠 host 分清「是新框架的协议，还是我这条链路上某个网关的脾气」。

## 两条元教训

回头看这些单元：**只有单元 0、单元 3、单元 4，以及单元 10 的 `KNOWN_*` 数据，是真正 harness 特有的。**

也就是说，做第二个 wire 分析器时，大约三分之二的问题你已经知道答案了。真正要重新投入的是
「这个 harness 到底声明了什么、又怎么组织它的请求」——而那恰恰是**必须靠 harness 自己的
声明 + 真实流量 + 人工 ground truth 才能回答的部分，没有任何捷径**。我们在请求归属上卡了
12 天，试遍了每一个"看起来合理"的信号。

如果只能记住两句话：

> ① **凡是"看起来合理"的判别信号，先假设它是错的，然后去真流量里证伪。**
> 这个项目里被真实数据推翻的合理假设，比被证实的多。
>
> ② **凡是 harness 自己声明过的事实，先去读，别猜。**
> 它声明的传输契约、它实际发送的字段、它自己的消费代码——三者都是现成答案，不需要等某个
> 上游把缺陷踩出来。

两条方向相反，合起来才完整：**该证伪的是自己的假设，该直接采信的是 harness 的声明。**
260731 那两次事故，恰恰是把这两件事做反了——对 harness 白纸黑字的声明视而不见，
对自己"官方 API 应该是这样"的印象深信不疑。

## 这份手册怎么来的、怎么维护

它是 260729 从 45 篇已归档的迭代记录 + 变更日志里蒸馏出来的——那些记录里有架构文档没有的东西：
**被否决的方案、真机铁证、根因链、"这个 bug 是第 N 次复现"**。

为什么要蒸馏而不是直接读原始记录：那些记录是**事件流**（一次改动的前因后果，写完就不再改），
而移植时需要的是**当前定论**（这类问题现在的答案）。而且它们体量比整套文档还大，每次重新归纳
一遍既贵又不稳定。

**维护方式**：不要重新蒸馏。每次有值得回看的改动归档时，回到对应单元补一条——如果它推翻了这里
的某个定论，就**改掉那个定论**，而不是在后面追加一段"但是后来发现"。这份手册是当前态，不是
时间线。
