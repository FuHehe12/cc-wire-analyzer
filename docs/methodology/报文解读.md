# CC Wire Analyzer 报文解读

> 读者：用这个软件看自己 Claude Code 流量的人——尤其打开捕获列表 / 时序 DAG，看到 `main` / `title` / `security` / `count_tokens` 这些 chip 不明白"这些请求到底是什么"的使用者（含非程序员）。
> 配套：[界面导览.md](../reference/界面导览.md)（kind 术语表 + 4 个视图）、[架构总览.md](../reference/架构总览.md)（软件怎么搭起来 + 分类逻辑）、[API契约.md](../reference/API契约.md)（接口规格）。
> 本篇讲：**CC 在一次会话里到底发了哪些请求、它们各自是什么、CC 为什么发它、你怎么认出它**。
> kind 的一句话定义在 [界面导览.md](../reference/界面导览.md) 核心概念表，本篇只做**展开解读**，不复制定义。

## 引子：你看到的请求，多半不是"对话"

打开 app，捕获列表里一长串请求。直觉上你会以为——这些都是我和 CC 的对话。

**错了。** 一天里相当一部分请求，CC 从没告诉过你它在发。它在自己的后台**数 token、审安全、起标题、压历史**，每一类都花着你的额度，而 CC 的界面、`~/.claude/projects/*.jsonl` 里**一个字都不会出现**。

举一条真实录制（就是催生这篇文档的那条）：

```
20:48:27.380 → 20:48:28.614   1.2s   ttft 1.2s   stream=否   output=0 token
path:  /v1/messages/count_tokens
发送内容：39736 字符的 CHANGELOG.md 全文
返回：    {"input_tokens": 9968}
```

`ttft 1.2s` 几乎等于总耗时 `1.2s`、`output=0`——这条请求读进去一大段文本，吐出来总共 21 个字节。它不是对话，是 CC 在问上游："我刚才读进上下文的这个文件，占多少 token？"——好决定要不要压缩、截断。

> 这条请求在 CC 界面里看不到，jsonl 里也没有。**只有 wire 层看得到。** 这正是这个工具的存在理由：让 CC 在你背后做的每一件事，都变成你能审计的记录。

认不清这 10 种请求，就读不懂时间线——你会把数 token 的探针当成卡顿，把安全审查当成对话，把子代理的噪音算进主线成本。这篇文档把它们逐一摊开。

## 先认 10 种 kind（判别顺序很重要）

CC 与上游的每一次请求，按"它想干什么"归 10 种 `kind`。判别**不是看一个字段**，而是按固定顺序逐条筛（来自 `src/classifier.py` 的 `classify_idx`，先命中的为准）：

| 顺序 | kind | 判据（先命中为准） | 为什么排这里 |
|---|---|---|---|
| 1 | `count_tokens` | **path** 含 `count_tokens` | 它连 `/v1/messages` 都不走，先按 path 拣出来 |
| 2 | `security` | system 文本含 `"security monitor"` | 必须在 title/main 之前——否则被主线指纹抢 |
| 3 | `title` | **官方位**：`output_config.format.type == "json_schema"` **且**无工具 | 260901：CC 让模型起名字时要结构化回包才声明 schema，真对话请求从不声明。措辞会被改（2.1.238 整段重写、七条措辞全失效），官方位不会 |
| 4 | `title` | 措辞兜底（`"5-10 word title"` 等） | 官方位没带时（老录制 / 未来换回非结构化回包）的退路 |
| 5 | `compact` | system 含 `"summary of the conversation"` | 措辞判定；压缩**带全量工具**，走不到第 8 条那道结构门，措辞是它唯一的防线 |
| 6 | `subagent` | 计费头 `cc_is_subagent=true` | 上游权威位，优先于一切主线措辞指纹 |
| 7 | `hook_eval` | system 含 `"stop-condition hook"` | StopConditions hook 评估（260802 固化）。**无工具**，260901 起必须排在结构门之前，否则被截成 `other` |
| 8 | `notify_eval` | 无工具 **且** system 含 `"whether to notify the user"` 等 | 走开通知的状态判定（260902 固化）。同上，无工具，排在结构门之前 |
| 9 | `other` | **结构门**：无工具但有 system 的对话形状请求 | 260901：真主线恒带全量工具清单（实测 3,352/3,352），无工具就不可能是主线。这道门把 fail 方向从「漏了就混进主线」翻成「漏了就显示成 `other`」 |
| 10 | `main` | system 含主线指纹（`"you are claude code"` / `"you are an interactive agent"`） | 主体对话 |
| 11 | `main` | 带工具兜底（未知形状默认主线） | 260725 方向反转：`sdk-cli` 主线不含指纹，判 subagent 会把 5/5 全降级 |
| 12 | `quota_probe` | `user="quota"` + `max_tokens≤1` + 无 system/tools | CC 配额嗅探（260802 固化）|
| 13 | `other` | 以上都没命中 | 残缺 / 未知形状；稳定的会陆续固化成专门 kind，并由 `/api/unknowns` 主动暴露 |

**两个关键点**，后文会反复用到：

1. **`count_tokens` 靠 path，其余靠 system 措辞或计费头**——没有一种 kind 是靠"流不流式"或"输出多少 token"判定的。这是识别的命脉（见[识别方法论](#识别方法论别被表面特征骗)）。
2. **判别顺序不可调换**。title/security 的 system 开头跟主线一模一样（都是 "You are Claude Code…"），把它们排在 main 之后，它们就会被主线指纹一口吞掉，永远认不出来。

## 10 种请求逐一解读

每种请求按同一个结构讲：**是什么 → 报文长什么样 → CC 为什么发它 → 怎么认 → 易混点**。

### count_tokens —— CC 在数 token

**是什么**：CC 估算"某段内容占多少 token"的探针请求。不生成任何内容，只拿回一个数字。

**报文形态**（真实录制）：

```
path:        /v1/messages/count_tokens     ← 注意：不是 /v1/messages
method:      POST
请求体：     { messages, model, tools }     ← 只有这三样，没有 system、没有 max_tokens、没有 stream
响应：       {"input_tokens": 9968}         ← 21 字节，一个数字
usage:       只有 input_tokens，没有 output_tokens
```

**CC 为什么发它**：CC 要管理上下文窗口。每当有新内容要纳入上下文（你读进一个文件、对话历史增长、工具结果回传），CC 先发一个 count_tokens 问上游"这段占多少 token"，再决定要不要触发压缩、要不要截断老消息。引子那条就是把刚读进来的 `CHANGELOG.md`（39736 字符）整段发去数，拿回 9968。

**怎么认**：**只看 path**。path 里带 `count_tokens` 就是它——这是唯一一种按 path 判定的 kind。

**易混点**：它和 security 在 surface 上像到能骗人（都非流式、output 都极少、input 都可能很大）。但它**没有 system**、path 不同、返回是裸数字。详见[识别方法论](#识别方法论别被表面特征骗)。

### security —— 后台安全审查

**是什么**：CC（尤其是自主模式下）在后台跑的安全监控——把 agent 的行为 / 内容发给一个分类模型审"这安不安全"，拿回一个严重度标签。每会话后台跑、用户完全无感、却花真金白银。

**报文形态**（真实录制，已脱敏——安全审查的 system 含用户身份与会话上下文，**不宜公开原文**）：

```
path:        /v1/messages
model:       claude-sonnet-5               ← 安全审查用的模型名
请求体 system 三块：
  [0] 计费头（cc_entrypoint=cli）
  [1] "You are a security monitor for autonomous AI coding agents…"   ← 命中判据
  [2] 会话上下文（含用户身份、规则）            ← 脱敏：不贴原文
max_tokens:  64                              ← 给分类标签的额度，很小
stream:      否（非流式）
响应：       <severity>8                     ← 一个严重度标签，output 约 9 token
```

**CC 为什么发它**：这是 CC 的安全防线。自主 agent 一边干活，这条监控一边在背后给每个动作打安全分。它的成本特征很特殊——`cache_creation` 巨大（实测一条 11 万 token 的缓存创建），因为它要把整套审查规则塞进缓存反复用。

> v0.2.0 曾有个 bug：非流式响应的 usage 解析只扫 JSON 顶层，恰好 count_tokens 的形状命中了那个错误分支，而**安全分类器恰好是非流式**——于是这个工具最该揭示的成本被自己扔了。详见 [架构总览.md](../reference/架构总览.md) 1.1 节。这是"只覆盖一条分支"教训的同型再现。

**怎么认**：system 文本里出现 `"security monitor"`（或 `"you are a security"`）。max_tokens 会变（注释里记过 2112，今天实测是 64），**别拿 max_tokens 当判据**。

**易混点**：和 count_tokens 表面像，但 security **有 system**（且含 security monitor 措辞）、path 是 `/v1/messages`、返回是 `<severity>` 标签不是裸数字。

### title —— 给会话起标题

**是什么**：CC 给当前会话生成侧边栏标题。用一个便宜的小模型，靠 system 里的 title 指令，输出一个短标题。

**报文形态**（真实录制）：

```
path:        /v1/messages
model:       glm-5v-turbo                   ← 用便宜模型
stream:      是                              ← 注意：是流式！
max_tokens:  32000                           ← 注意：不是小额度
请求体 system 三块：
  [0] 计费头
  [1] "You are Claude Code, Anthropic's official CLI for Claude."   ← 和主线同款身份句
  [2] "Generate a concise, sentence-case title (3-7 words) that captures the main topic…"  ← 命中判据
tools:       无
响应：       {"title": "继续开发 cc-wire-analyzer 项目"}   ← 一个标题，output 约 14 token
```

**CC 为什么发它**：侧边栏要显示会话名。CC 周期性地（或在会话开头）用轻量模型给对话起标题，避免让你看到一串无意义的会话 id。

**怎么认**：system 里出现 title 措辞（`"5-10 word title"` / `"sentence-case title"` / `"captures the main topic…of this coding session"` 等）。**必须排在 main 之前判**——title 的 system[1] 跟主线一模一样。

**易混点 / 反直觉**：title **是流式、max_tokens 是 32000**，跟"轻量小请求"的直觉相反。这正说明**判据是 system 措辞，不是 max_tokens / stream**。（开发用的样例数据里 title 写的是 `stream=False, max_tokens=512`——那是**形状占位，不是真实值**，别照抄。）

### compact —— 压缩上下文

**是什么**：上下文快满时，CC 把历史对话压成一段摘要（autocompact），腾出空间继续。

**报文形态**（来自开发样例，照真流量形状复刻）：

```
path:        /v1/messages
请求体 system 三块：
  [0] 计费头
  [1] 身份句
  [2] "You are a helpful AI assistant tasked with summarizing conversations."   ← 命中判据
messages:    [user: "Your task is to create a detailed summary of the conversation so far…"]
响应：       一段长摘要（output 可达 2000+ token）   ← 和 title/security 相反，输出很长
```

**CC 为什么发它**：上下文窗口有限。当历史太长，CC 不是简单截断（会丢上下文），而是先压缩成摘要再继续——代价是生成摘要这一笔开销。这一类请求平时看不到，但**一旦你的会话变长，它会周期性出现**，是长会话成本的一部分。

**怎么认**：system 或 user 文本里出现 `"detailed summary of the conversation"` / `"summary of our conversation so far"` 等措辞。输出明显比 title/security 长。

**易混点**：和 title 都"靠 system 措辞、都生成文本"，但 compact 输出长摘要、措辞是 summary 不是 title。判别顺序上 compact 排在 title 之后。

### main —— 你和 CC 的对话主线

**是什么**：真正的对话请求——你发消息、CC 回复、调工具、继续。一天里数量最多（本会话实测占全部请求的绝大多数）。

**报文形态**（真实录制）：

```
path:        /v1/messages
model:       claude-opus-5 等
stream:      是
请求体 system 三块：
  [0] 计费头（cc_version / cc_entrypoint）
  [1] 身份句（"You are Claude Code…" 或 sdk-cli 模式的 "You are a Claude agent…"）
  [2] 主体准则（真正的"系统提示词"，含 currentDate 水印、CLAUDE.md、工具说明等）
tools:       几十个（Bash / Read / Edit / Task / …）
messages:    完整对话历史
响应：       thinking + text + tool_use 块（stream=True，逐字吐）
```

**CC 为什么发它**：这是你和 CC 协作本身。一次"轮次"可能拆成多条 main 请求（你发消息 → CC 调工具 → 工具结果回传 → CC 继续），DAG 上用 `turn_start`（轮次起点）和 `pure_chat`（纯对话轮）区分。

**怎么认**：system 含主线指纹 `"you are claude code"`（交互模式）或 `"you are an interactive agent"`（`claude -p` 的 sdk-cli 模式）。兜底：带工具 + 有 system、且没命中前面任何 kind → main。

**易混点**：sdk-cli 模式的主线 system[1] 是 `"You are a Claude agent…"`，**不含** "you are claude code" 指纹——v0.4.0 前这种主线全被判成 subagent（5/5 错），是旧版准确率 10/15 的全部错项。现在靠"带工具兜底判 main"修掉了。

### subagent —— CC 派出去的子代理

**是什么**：主线响应里调了 `Task` / `Agent` 工具，派生出一个子代理去干子任务。子代理自己有一串请求，也经过 wire 层。

**报文形态**（来自开发样例，照真流量形状复刻；本会话未派子代理，无真实样例）：

```
path:        /v1/messages
请求体 system 三块：
  [0] 计费头：…cc_entrypoint=sdk-cli; cc_is_subagent=true;   ← 命中判据（权威位）
  [1] 身份句（和主线同措辞！）
  [2] agent 专属词（"You are a file search specialist…" / "software architect" 等）
messages[0]: <system-reminder>…注入上下文…</system-reminder> + 派生 prompt   ← reminder 在前
```

**CC 为什么发它**：主线把一个子任务（"去调研 X"、"去搜索 Y"）交给专门的子代理，自己等结果。子代理复用父会话 id（所以 session id 只能当泳道键，不能判身份），靠计费头 `cc_is_subagent=true` 区分。

**怎么认**：**只认 system block[0] 计费头的 `cc_is_subagent=true`**。这是 CC 在 wire 上自己标的权威位（260725 实测 8/8 子代理带、7/7 非子代理不带）。

**易混点 / 血泪史**：曾经试过用 session_id、entrypoint、"有没有 Agent 工具"、system 措辞来判子代理，**全错**——子代理复用父 session_id、继承 entrypoint、general-purpose 子代理带着 Agent 工具、block[1] 和主线同措辞。只有计费头靠谱。详见 [架构总览.md](../reference/架构总览.md) 2.1 节。

### quota_probe —— CC 在探"我还能不能用"

**是什么**：CC 发的极小探测请求——`messages=[{role:user, content:"quota"}]`、`max_tokens=1`、无 system、无 tools、非流式。一次只要 1 个 token。

**报文长什么样**：
```
path:   /v1/messages
body:   {model, messages:[{role:"user", content:"quota"}], max_tokens:1, stream:false}
status: 多为 429 / 401 / timeout / connect failed
```

**CC 为什么发它**：配额 / 鉴权健康检查。CC 用这个极小请求探"当前 token 还能用吗、配额够不够"，再决定要不要提示你、要不要重试。实测 9 条**全部**返回错误——这不是失败，是探测本身要的反馈。**主对话里完全看不到**，是 CC 的后台隐藏行为，只有 wire 层才看得见。

**怎么认**：`user="quota"` + `max_tokens≤1` + 无 system/tools。判据极硬（铁证一致）。260802 前落 `other`，现固化成专门 kind。

### hook_eval —— StopConditions hook 的模型评估

**是什么**：你在 CC 配了 `StopConditions` hook（"满足某条件就停"）时，CC 把对话 transcript + 你设的停止条件打包发给模型，要它判条件满足没。

**报文长什么样**：
```
system:   "You are evaluating a stop-condition hook in Claude Code…"
messages: [会话 transcript…, {user: 判断指令 + Condition: <你的停止条件>}]
format:   output_config.format = json_schema（强制结构化输出）
resp:     {"ok": true/false, "reason": "..."}
```

**CC 为什么发它**：hook 机制——让你用自然语言设停止条件，CC 用模型当裁判。既不是用户对话、也不是 title/security/compact，是无 tools 的评估请求。

**怎么认**：system 含 `"stop-condition hook"`。260802 前落 `other`，现固化。

### notify_eval —— 你走开之后，CC 在判"要不要叫你回来"

**是什么**：你把任务丢给 CC 就去干别的了。CC 每隔一阵子把"刚才这段尾巴"发给模型，问它现在是
done / working / blocked 里的哪一种——判成 `blocked` 就推手机通知把你叫回来，其余不打扰。

**报文长什么样**：
```
system:   两块（计费头 + 16,683 字的判定提示词，开头逐字是
          "A user kicked off a Claude Code agent to do a coding task and walked away…
           so the system knows whether to notify the user."）
messages: [{user: "Current state: working (for 2m) / Tool calls so far: … /
            User's most recent ask: … / Assistant message tail (last 756 chars): …"}]
tools:    0 个        max_tokens: 1024      无 betas / 无 output_config
resp:     {"state":"working","detail":"…","tempo":"active","output":{}}
```

**CC 为什么发它**：通知策略要在"少打扰"和"别让活儿干等着"之间做取舍，这个取舍 CC 自己用规则
判不了（"我读完了文件"到底算干完还是干到一半？），于是外包给模型。**同一轮工作期间会反复
发**——实测同一天出现 `for 0m / 1m / 2m / 3m / 8m / … / 22m`，等得越久发得越稀。

**怎么认**：无工具 **且** system 含 `"whether to notify the user"` / `"decide which of four
states it's in"`。跨版本稳：2.1.251 与 2.1.258 两版提示词 16,683 字**逐字相似度 0.9998**，
唯一差异是计费头里的 `cc_version`。260902 前落 `other`，现固化。

**为什么它值得单列**：它是 aux 里数量最大的一族（全语料 18 条，仅次于 security），而且是
**主对话完全看不见的后台行为**——CC 替你做的"要不要打扰你"这个决定，只有 wire 层看得到。

### other —— 认不出的残缺请求

**是什么**：以上都没命中的请求。通常是**形状残缺**——缺 system、来自未知 harness、或录制中途截断。正常流量里很少见。

**怎么认**：fallback。既没有计费头权威位、又不带工具、system 也不含任何已知措辞。

**怎么办**：如果你看到大量 `other`，多半是遇到了新的 CC 版本 / 新 harness 形态。先调 `/api/unknowns` 看「已知集合外」的值（非标块类型/字段、未解析请求字段、beta 长尾）——它是为发现协议演进准备的盲区雷达；再跑 `tools/lane_probe.py` 把权威位 / session_id / entrypoint / 措辞指纹摊开核对。

## 识别方法论：别被表面特征骗

这是本篇最重要的实操结论，也是催生这篇文档的那次误判的教训。

> **判断一条录制"是什么请求"，权威依据是 `path` + `response.body_text`（或 system 措辞），不能只靠 `stream` / `output` 这些表面特征推断。**

为什么？因为多种请求在表面特征上**高度撞脸**，但本质完全不同：

| 表面特征 | count_tokens | security | title |
|---|---|---|---|
| 非流式 | ✅ | ✅ | ❌（其实是流式） |
| output 极少 | ✅（0） | ✅（约 9 token） | ✅（约 14 token） |
| input 可能很大 | ✅ | ✅ | 看情况 |
| **本质** | 数 token 的探针 | 安全审查 | 起标题 |

只看"非流式 + output 少"，你**无法区分** count_tokens 和 security——但它俩一个是数 token、一个是审安全，八竿子打不着。本文档作者就因为这个把一条 count_tokens 误判成 security classifier，被用户当场纠正。

**正确的识别顺序**（按这个查，几乎不会错）：

1. **先看 path**：带 `count_tokens` → count_tokens，结束。
2. **再看 system 措辞**：`security monitor` → security；title 措辞 → title；summary 措辞 → compact。
3. **再看计费头**：`cc_is_subagent=true` → subagent。
4. **最后看身份指纹 + 工具**：主线指纹或带工具 → main；都不沾 → other。

在 app 里，详情视图左栏能看到 `method + path`、折叠的 `System blocks`（展开看 block 措辞）、右栏能看到 `response` 的 content。**先看 path，再展开 System blocks 看措辞**——这两步就能认出绝大多数请求，不需要去猜 stream / output。

---

## system 三 block：一条请求的"信封"

几乎所有对话类请求（main / subagent / title / compact / security）的请求体里，`system` 都是**固定三块**的结构。把它当成一封信的"信封 + 正文"来理解，很多困惑就消失了：

| block | 装什么 | 性质 |
|---|---|---|
| **block[0]** | 计费头：`cc_version` / `cc_entrypoint` / `cc_is_subagent` | 元数据。身份与计费，`cc_is_subagent` 是判子代理的权威位 |
| **block[1]** | 身份句："You are Claude Code…" 或 "You are a Claude agent…" | 固定身份声明。主线和子代理**同措辞**，所以不能靠它判身份 |
| **block[2]** | 主体准则 / 任务指令 | 真正的"系统提示词"。main 是对话准则；title/compact/security 这里放任务指令；subagent 放 agent 专属词 |

**为什么这么设计**（CC 的分组思路，值得借鉴）：元数据（计费/身份）和正文分离——身份可缓存、正文可按需重组。block[1] 带 `cache_control`，CC 把固定的身份句缓存起来反复用，省 token。

> **一个会咬人的认知陷阱**：block[2] 的主体准则**不是固定文案**——它是 Anthropic 用 Growthbook A/B 实验**动态组装**的。同一段（如 `operating autonomously`、`# Delivering work`）受独立 feature flag 控制，你被分到的实验桶变了，system 就变了，**和本地 CC 版本、模型都无关**。
>
> 这意味着：两次会话的 system prompt 不同，**未必是 bug**，可能只是实验分组不同。别像本文档作者那次调查一样，看到"system 变少了"就以为是出错——先想是不是实验桶变了。（完整调查见本地 `issues/open/260728_system_prompt实验溯源探讨.md`，不上传开源仓库。）

而 count_tokens 是个例外——它**没有 system**（数 token 不需要指令），请求体只有 `messages + model + tools`。这也是它最快能被认出的特征之一。

## 收束：看懂报文，才知道 CC 替你做了什么

CC 一次会话发出去的请求，远不止"你一句我一句"。它在自己后台数 token 管上下文、审安全守防线、起标题给你看、压历史腾空间，主线之外还可能派子代理——这些事每一件都花着你的额度，而 CC 的界面里一个都不显示。

认得这 10 种请求，你才能：

- 把"今天 token 花在哪了"算清楚（数 token 的探针、安全审查的缓存，都是隐藏成本）；
- 把时间线读懂（哪些是主线对话、哪些是后台噪音、哪些是派生出去的子代理）；
- 把异常归对因（一条卡顿的请求，可能是 count_tokens 探针，不是上游慢；一组 400，可能是 title 生成被 effort 配置挡了，不是对话出错——见 [界面导览.md](../reference/界面导览.md) 失败聚合）。

> 这个工具把 wire 层的真相录了下来——这是从 0 到 1 的硬骨头。但**录下来不等于看得懂**：一串 `main` / `security` / `count_tokens` 的 chip 摆在面前，不认识它们，再全的录制也只是字节。这篇文档想做的，是给那些字节贴上"这是什么、CC 为什么发它"的标签——让记录从**可观测**变成**可读懂**。
